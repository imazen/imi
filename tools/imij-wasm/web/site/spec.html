IMI format, version 4

Status — V4 is implemented on main and remains unreleased. Implementation coverage records native x86 and ARM, i686 library, no_std, browser, gigapixel, and Atlas checks. The structural decoder audit originally identified exact-packing geometry and index proof obligations; section 11 records their resolution and the corresponding production validation. Ordinary image, row/group, frame/page and common bounded writers now emit header version 4. Explicit legacy writers retain their earlier V3 contracts. Base-V4 browser pixel/range, explorer and Atlas trace/grid/encode checks pass in three engines for the frozen source recorded in the implementation report. Native-directory open and crop pass through the local production browser reader. Live CDN qualification and browser coverage for scoped checks remain separate. The complete site is packaged separately from deployment. Windows qualification and the other release-platform CI checks remain required before publication; these gates do not constitute a release. This document defines the V4 replacement grammar. SPEC.md remains the implemented V2/V3 reference and supplies the unchanged sample, transform, quantizer and entropy arithmetic cited below. The independent design review records alternatives, access costs and corrections to the review; it adopts no grammar change.

Pre-freeze additions, 2026-11-17: section 6.2 specifies counted integrity lists and independent group/tile raster checks. XXH3-64/128 and optional BLAKE3 generation and verification are implemented. Keyed and public-key suites have opaque framing. The native directory proposal still records separate pyramid-directory and public exercise work before freeze. See the pre-freeze wire choices for the FourCC decision and the gigapixel and digest design tradeoffs.

V4 makes defaults, model definitions and geometry part of one lossy grammar. They are no longer optional parallel ways of interpreting an AC prefix. Both AC coders and the existing transform choices remain available. Recovery of the original bytes of an input JPEG is outside the V4 format scope.

1. Version boundary and unchanged parts

The signature is unchanged. The header version byte is 4. Header fields, canonical u64 LEB128 integers, record framing, chunk framing, metadata, feature admission and checksum algorithms retain their V3 meanings unless overridden here. All integers introduced below are canonical uvarints. Fixed-width end-anchored locator fields remain fixed-width. IDs never size allocations.

V2/V3 readers remain separate compatibility parsers. They translate into the same checked internal descriptions as V4. V4 does not probe for an old grammar inside a new payload. Existing readers reject version 4 before pixels. Merely changing an existing file's version byte is not an upgrade.

V4 writers use kVAL for typed attributes on ordinary images, sequence items and inside sDEF. The attribute payload, limits and merge rules are unchanged. Readers also accept kVMD from earlier files. The two FourCCs identify one slot and may not coexist in it.

Physical transport splitting is outside the image grammar. A complete image remains one logical byte stream; offsets and checksums refer to that stream. Its header carries no physical part size or part count. A transport manifest must supply the mapping from logical offsets to separately stored objects. Changing that mapping alone does not change image bytes. Spatial tiles below are codec access units, not transport parts; a part boundary may cross a tile. This imposes no advance encoded-length requirement on a streaming writer: its transport can finalize part count and total length when output completes.

V3 feature bits 26–31 describe replaced syntax and are reserved, required zero in V4. Other feature declarations still gate actual algorithms: merged/small transforms, alternate sample maps, explicit quantization tables, and so on. Core V4 syntax needs no second feature bit to turn it on. Profile versions remain human-facing feature bundles.

samples_32 (feature bit 15) declares 32-bit sample coding. U32, I32, F32 and 64-bit sample declarations imply it, including when the actual coded width is narrower. Lossy DC storage 1 (I32) requires it even when the output sample type is narrower. Enclosing collections declare the features required by their contained images under the existing nesting rules. The reference decoder requires extended for samples_32; thus it can reject a file using this capability before decoding DATA. The baseline reference build decodes U8, U16 and F16. Sample IDs, feature IDs, and encoded bytes keep their existing meanings.

near_lossless (feature bit 4) declares bounded residuals in numeric models. It is independent of sample width and DCT coding. An exact-model reader may refuse this feature as Unsupported and still decode ordinary lossy images with exact numeric DC. The Rust near-lossless option supplies the bounded reconstruction kernels. Exact-model builds also check this capability when entering nested numeric models or independent plane tile codestreams. A missing required declaration in the local file is Corrupt. Native view directory and integrity semantics apply to both reader configurations.

Header channel layout 8, Scalar is available in versions 3 and 4. It has one stored numeric component, zero color components and no alpha. It requires pixel_models and numeric coding (header coding byte 0). The CICP tuple is 2, 2, 0, 1 (unspecified primaries and transfer, identity matrix, full range). Scalar slot order is its single component, with high and low words in the existing order for wide samples. Gray remains visual luminance, with the existing sRGB default. Channel values 9–11 remain unassigned.

V4 structural and admission failures return directly; they must not trigger an unadmitted checksum rescan on an error path. For parseable files, supported container checksums are verified under the request's work/cancellation policy. This does not change V2/V3 checksum-error explanation behavior.

1.1 Plane-set composition

Plane role 14, Scalar describes a non-color plane. It has unspecified CICP, no ICC reference, and levels with numeric Scalar tiles. The reference plane reader and writer admit up to 1,024 planes by default, subject to the independent directory, level and request budgets.

The reference sparse plane API defaults to addressability of 2^40 pixels per level and 2^46 bytes per file. Positional ranges and cumulative record lengths use checked 64-bit arithmetic. Opening charges directory and checksum table capacity separately. Each ROI admits the page and tile bytes it needs and checked sample work independently of canvas area. Optional checksum rounding admits the pieces it will read before reading them. Full-raster APIs apply their output limits before allocating.

The default sparse release gate opens a 32,768 × 32,768 paged view, reads a bottom-right crop from a tile beyond an 8 GiB offset, and checks exact output and untouched row padding. The file is generated by the same forward plane writer through a write-only destination with caller-owned index scratch. Sparse and metadata access measurements record the observed read costs and the browser controls.

A plane set retains its existing outer pDAT / pIDX / sLOC structure and versioned directory IDs. Its primary V4 image uses front or no unit directory: a tail unit directory must be the final image chunk, which would conflict with the appended plane records. An encoded-domain writer can relocate the directory from tail to front without changing setup, object bytes, relative object offsets, entropy or local digest identities. Absolute plane offsets and the outer encoded checksum are finalized after that relocation.

Each independently encoded plane tile remains a complete image. A V4 tile may contain its DATA and its ordinary final uIDX; it cannot introduce metadata, frames, nested plane sets or temporal references. Stored sample, precision, color, orientation and component geometry must match the existing plane profile. Each tile selects its own header version and explicit payload reader. Migration rewrites every image tile, retains opaque attachments and ancillary directory records, and rebuilds offsets under the caller's byte/depth/plane limits.

1.2 Native image views

Optional critical pIDX record 101 supplies native original/reduced/preview view discovery. It reuses existing primary and plane-level storage; it creates no additional pixel payload or second tile table. It is legal only beneath a V4 primary. The directory selects either the existing flat record table or the paged record authority in section 1.3. Both retain fixed sLOC discovery.

All fields in record 101 are canonical uvarints except explicit UTF-8 bytes:


schema = 1, original_view_id, view_count
repeat view_count, strictly increasing view_id:
    view_id
    role                    0 original, 1 reduced, 2 preview
    label_bytes, label      bounded UTF-8, nonempty, no NUL
    backing                 0 primary; 1 plane level
    if backing == 1: plane_id, level_ordinal
    registered              0 unregistered, 1 explicit mapping
    if registered == 1, for x then y:
        scale_numerator, scale_denominator
        zigzag_offset_numerator, offset_denominator

There is exactly one role-0 entry, named by original_view_id; zero is a valid ID. No ID sizes an allocation. The original has no registration and defines the reference grid. Other views map directly into that grid, with no recursive view references or parent graph. An absent mapping explicitly means unregistered; dimensions alone do not establish pixel-center alignment.

Each axis maps native, unoriented pixel-edge coordinates as original = offset + scale * view; a pixel center has coordinate i + 1/2. Scale numerators/denominators and offset denominators are nonzero; scale is positive. Each fraction is in reduced form, including zero offset as 0/1. Offset numerators use canonical u64 zigzag for signed i64 values. The directory performs no resampling, color conversion or orientation transform.

Primary backings inherit the stored primary header and metadata. A plane-level backing selects the existing level's complete native packed-color backing; component references, dimensions, precision, type and CICP come from the checked plane descriptors. That profile requires straight alpha and orientation 1; calibration/ICC references remain the existing attachment references. All components must have one complete compatible backing. No duplicate dimensions, color contract or payload spans are stored in a view. Unknown schemas, roles or backing kinds are Unsupported; missing references, duplicate IDs and noncanonical mappings are Corrupt before pixel reconstruction.

PlaneSetLimits::with_views bounds the count (default 1024); existing label and index-byte limits bound strings and record bytes. Existing planes/levels and primary ROI readers reconstruct the selected view. Ordinary primary decoding retains its existing behavior, including files with no native view directory.

The native directory is authoritative for pyramid discovery, registration and tile extents. An archive index serves item lookup and carries small search summaries. A publication catalog binds the file to its URL, immutable length and any part mapping. A client may retain verified native extents for reuse. Publication catalogs need only the information required to locate and open the chosen representation.

An application can publish advisory startup ranges for an immutable native file and selected view. It can also publish exact copies of those file bytes in a cache object. Readers use the file's usual validation and directory discovery with the resulting byte cache. The startup profile adds no V4 records and leaves the file's offsets and integrity scopes intact.

1.3 Paged native records and forward publication

A V4 plane directory contains exactly one record authority: flat record 93 (the retained pDAT form), or critical record 99 below. Both use the same plane/level, attachment and optional image-view descriptors. Record 99 is illegal beneath V2/V3. Mixing the two authorities is Corrupt.

The paged physical order is:


primary image (front/no uIDX)
pREC ... pREC              contiguous bound native tiles/opaque attachments
pIPG ... pIPG              contiguous independently checked record pages
pIDX                      bounded packed metadata and page root
sLOC                      unchanged fixed 37-byte locator

Every chunk has the ordinary bounded tag, uvarint(body_bytes + 1), body framing. A pREC body is record_id, original_payload, where record_id is a canonical uvarint. IDs are consecutive zero-based ordinals in physical order; tile and attachment descriptors select these ordinals. Native tile payloads remain complete independently decodable images. A V4 native tile can retain its cSUM and pSUM before DATA and an optional uIDX after DATA. Readers verify supported encoded checksums before reconstructing the tile and supported pixel checksums before supplying its pixels to a view. The distinct pREC tag exposes its identity framing before finalization; pDAT never changes meaning.

Record 99 contains canonical uvarints and fixed 16-byte digests:


schema = 1 or 2
record_count                  positive u32
records_per_page              power of two, 16 through 4096
records_end                   absolute end of the last pREC
repeat ceil(record_count / records_per_page):
    data_bytes                complete framed pREC bytes covered by this page
    packed_page_bytes         pIPG body length, 1 through 65536
    page_digest               XXH3-128, 16 canonical digest bytes
attachment_length_count

    record_id, original_payload_bytes

The first page's data starts at primary_len (record 91); subsequent starts are cumulative data_bytes. The first pIPG starts at records_end; subsequent page starts are cumulative ordinary framed chunk lengths. The data extents must end exactly at records_end, and the pIPG extents exactly at pIDX. No second array of absolute per-record offsets is stored. The final page holds the remaining records; all earlier pages hold records_per_page records.

The attachment-length declarations cover exactly the attachment descriptor IDs. They preserve zero-I/O length discovery and do not supply offsets. Each selected leaf must agree with the declared original length. Ordinary image lengths remain only in leaves. Unknown schemas are Unsupported; malformed counts, bounds, coverage, lengths or identities are rejected before using the selected record. Counts, root expansion, page allocation and request work are bounded independently of encoded file size. Readers may fetch independent selected leaves in one positional source batch. Each leaf still validates against its own root descriptor before its records are used.

A pIPG body uses the existing metadata_pack envelope. Its expanded bytes begin with first_record_id, page_record_count. Schema 1 then contains positive varint lengths. Schema 2 allows those same lengths or the packed form identified by a zero in the first length position.


first_record_id, page_record_count
plain:
  repeat page_record_count:
    pREC_body_bytes            includes the canonical record_id prefix
packed (schema 2):
  0, base                      positive uvarint base length
  width                        u8, 0..32
  residuals                    page_record_count values, width bits each, LSB-first

Each packed length is base + residual with checked addition. Width zero sets every residual to zero. The packed byte length is exactly ceil(page_record_count * width / 8), with zero high padding bits in the last byte. Both forms cover the same record ordinals and carry the same lengths including record ID prefixes. Writers compare the completed metadata-packed leaves and emit schema 2 only when at least one leaf uses the compact form. Readers that lack schema 2 reject it at the root.

Expansion is limited to 65536 bytes. Complete record offsets are inferred by summing their ordinary chunk lengths. The lengths must cover the root's data extent exactly. Before parsing a leaf, verify XXH3-128 over, in order:


ASCII "IMI/v4/plane-record-page" followed by NUL

The root's digest is the 128-bit XXH3 integer in little-endian byte order. The selected pREC must then carry the requested ID and expected native header. A forged root cannot silently redirect one tile to another valid tile merely by supplying its offset. This is an accidental-corruption/consistency check, not cryptographic authentication. An enclosing supported cSUM remains an independent encoded-file check. Opening checks the root and metadata, not unfetched page contents or entropy. Full validation walks every leaf and record. A sparse read verifies only its selected pages and tiles.

A forward writer declares the bounded plane/view layout, publishes complete pREC records in physical order, and spools only their lengths in caller-owned scratch. Completed records can be flushed before any pIPG, pIDX or sLOC exists; publication is provisional until finalization. Finishing checks/replays scratch, emits one bounded leaf at a time, then the small root and fixed locator. Neither the wire nor this schedule requires seeking in the destination, retaining a whole raster, buffering a whole output, or retaining a per-record array. Metadata and the page root still grow with levels/attachments and page count.

The current PlaneSetWriter accepts a V4 primary without an enclosing cSUM and retains supplied child checks. It refuses a primary requesting complete-file cSUM before publishing bytes; that policy needs replayable/seekable destination output. The buffered builder still supports cSUM with both authorities. Scratch, output or validation errors prevent successful finalization; early published records remain provisional. These implementation limits do not add wire flags.

1.4 Reconstructed floating-point guarantees

Optional outer header record 6 declares excluded IEEE classes for each channel of the reconstructed image. It is even and can be skipped by readers that do not use it. Its scope is the stored channels of this header's image. Previews, later sequence items, and nested plane tiles have their own headers. The declaration has no effect on entropy or sample reconstruction.


version     u8                 1
excluded    u8 × channel_count  stored channel order

In version 1, bit 0 excludes all NaNs, bit 1 excludes both infinities, and bit 2 excludes both signs of subnormal. Bits 3–7 are reserved and zero. A zero mask makes no claim for that channel. All-zero declarations are omitted. The record is valid only for F16, F32, and F64. A recognized version with the wrong length, a reserved bit, an all-zero list, or a non-floating storage type is corrupt. Readers skip unknown versions without using any guarantee. An empty record is corrupt.

Verification classifies the original exponent and fraction bits at the stored width. It occurs before widening, calibration, or conversion. Both signed zeros are allowed. The guarantee applies to reconstructed samples, irrespective of the encoder's source, and excludes row padding. Exact writers can verify the source directly. A forward writer can write the declaration in its opening header and check each group before publishing the group's bytes. A producer must finish successfully for the declaration to cover a complete image.

A reader can inspect the bounded header before requesting pixels. Strict validation checks every reconstructed sample covered by a recognized guarantee. A checked crop or group establishes the guarantee for the samples it checks. A declaration from an untrusted producer requires sample verification before it can drive a specialized kernel. File checksums check the declared bytes and do not authenticate the producer or establish sample-class guarantees. The ordinary decoding contract returns the stored samples. Calibration ranges and missing-value rules in SPEC 1.5 are separate.

2. Payload setup

Every DATA payload begins with a canonical uvarint setup byte length followed by exactly that many immutable setup bytes, then the common directory-placement prefix of section 6, then framed objects. The image header selects numeric/Quick or lossy setup grammar; readers do not probe both. Placement/reservation bytes are outside setup so a seekable writer can patch them without changing object integrity contexts.

2.1 Numeric and Quick setup

A standalone lossless/Quick setup contains, in order:


tile_cols, tile_rows, tile_order, object_integrity    uvarints
numeric_head                                       V3 numeric head grammar
scoped_checks                                      optional suffix, section 6.2

The four spatial/integrity fields have the same meanings as below. Derive the coding-group grid from the numeric head's stripe rows/column width and image geometry. Its fixed root models, maps, sample arithmetic, Quick controls and remaining numeric head records retain V3 meanings. Standalone research bank bit 2 is not allocated here. No record-63 model switching is introduced for standalone numeric/Quick; its main records remain kind 59 with mandatory unit_id followed directly by the existing stripe entropy.

Writer policy is independent of this grammar. Completed ordinary numeric/Quick images use one coding-group column per spatial tile and a front directory. A tile contains one native stripe, or enough shorter stripes for a nominal height of at least 64 pixel rows, clipped at the image edge. This bounds fetch granularity without a marker pair per tiny source stripe. Large-image crops avoid the previous image-sized tile policy and directory EOF probe. Explicit spatial writers retain caller-selected multi-group tiles and order; forward-only writers retain their publication and index strategy. Old valid V4 tile layouts and tail directories remain readable. Re-upgrading an already-V4 file retains its bytes rather than silently retuning its layout.

Legacy index/reservation/ordinal head records 10, 12 and 37 are invalid. Directory placement is common to all payloads and is not a numeric model record. Numeric root models belong to setup rather than separate directory entries. A numeric directory's main entries use role 0 and follow each tile's complete group schedule. Ignorable even objects may occur before/between tiles or between their children, without advancing that schedule; their ordinal is global among ignorable objects.

The semantic setup is the four spatial/integrity values and complete immutable numeric head above; its outer length and following placement are not part of those bytes. Directory/padding bytes have separate index/input/work admission rather than inflating the semantic header budget. Explicit numeric outer-file, forward-directory, ordinary entry points and indexed-tile adapters are implemented; their qualification is tracked in the implementation coverage.

This setup has no nested DC stripe height, DC column width or repeated image dimensions. Numeric model definitions contain interpretation and probabilities, not another geometry declaration. Alpha rectangles follow AC units; exact rectangles follow their tile's packing declaration; DC rectangles follow coverage.

  • 1: the existing four-4×4-plane path of V3 2.11.
  • 2 + layout: the existing channel-layout algorithm and byte code from

    • subblock.rs. The valid layout bytes are 0..11, except 8: full 8×8 is represented only by plan 0. The arithmetic and coefficient arrangement of the selected path remain distinct and unchanged.

Unrecognized plan codes are Unsupported. Existing capability requirements still apply. A merged parent must have plan 0 on its affected color planes; merging missing edge parents, or selecting an incompatible plan, is Corrupt. Plane plans for absent edge parents create no samples; only present parents are reconstructed. No new transform, sampling scheme or rounding rule is introduced.

An AC unit's settings is empty to inherit the image throughout. The nonempty forms are:


sparse  = group_selection, override_count, overrides...
range   = 3, group_selection, partition_byte_count, partition_bytes,
          override_count, overrides...
joint   = 4, joint_range_bytes
override = position_gap, cell_selection

A selection is 0 inherit, 1 inline delta, or 2 followed by a defined set ID. Markers 3 and 4 are single bytes and occur only at the beginning of their respective forms. Counts and positions are varints. Sorted positions and gaps follow V3 2.15. After resolving the group selection, the range form replaces its partition field with the decoded partition at each transform cell. Any sparse override then applies to that cell's state. Plane plans and AC scales inherit from the group and can still be overridden. Every transform cell resolves independently. The 16×16 settings positions called "tiles" in V3 are transform cells here. A spatial tile is the larger disk layout unit of section 5.1. These forms are the V4 partition and plane-plan prefixes.

The range form uses the probability model, raster traversal, symbols, neighbor classes and range arithmetic of V3 2.9.2. The coder and all contexts start fresh for each AC group. An odd bottom-right singleton cell has partition zero and consumes no bits. Every coded symbol must fit its cell's available parents before sparse overrides. The range form requires Superblocks and at least one nonzero map symbol.

The map uses strict termination. The encoder emits the lower endpoint of the final interval with the existing five-byte carry flush, discards the leading carry byte, and retains all remaining bytes including terminal zero bytes. The decoder takes four initial bytes and one additional byte per renormalization. It must consume exactly partition_byte_count bytes and finish with code = 0. Missing bytes, unread bytes, an invalid symbol, or a nonzero final code are Corrupt. The length must be between 4 and 4 * cell_count + 4 inclusive. Range state never crosses an AC group boundary. Group and spatial-tile index entries and publication order follow the existing framing.

For a transformed parent, AC code 0 restores ordinary numeric AQ, or 64 when AQ is absent. A positive code replaces that multiplier. It does not multiply an already applied AQ value. Exact and keep decisions are evaluated first; settings never turn bypassed parents into transformed parents. DC steps stay unchanged. The a/64 multiply uses the existing operation order.

3.1 Joint partition and 4×4 range form

The joint form requires the built-in image defaults and the SmallTransforms capability. Each group starts a new range stream. Bits use the same 32-bit range, 12-bit probabilities, adaptation by 1/32 and byte renormalization as the partition range form. Every probability starts at 2048.

1. Read one bit with a fresh probability. A zero gives partition 0 for every cell. A one requires Superblocks and codes the partition symbols with the same model and cell raster traversal as the partition range form. At least one cell must then be merged. Every footprint must fit inside the group. 2. Continue the same range stream over present unmerged 8×8 parents in parent raster order. Read a bit under one of four probabilities indexed by 2 * (left_mask != 0) + (upper_mask != 0). Zero gives mask 0. Outside the group and in merged parents, neighboring masks are zero. 3. For a nonzero mask, read flags in color-plane order. The plane probability index is 8 * plane + 4 * left_flag + 2 * upper_flag + luma_flag. The luma term is zero for plane 0 and otherwise this parent's plane 0 flag. If the first two flags are zero, infer one for plane 2 and consume no bit for it. Each set flag gives plane plan 1. Other present planes use plan 0.

At least one plane flag must be set. AC multipliers inherit numeric AQ throughout. The joint form has no group delta, override list or nested stream length. Its one range endpoint consumes exactly the bytes after marker 4 and leaves a zero decoder remainder. The stream has at least four bytes and at most 4 * (cells + parents) + 5 bytes, using the whole group geometry. Readers validate the map before delivering resolved settings. Group and tile boundaries, model references and coefficient syntax follow the same rules for all settings forms.

A one-parent group with an ordinary partition and only plane 0 using four 4×4 transforms has settings bytes 04 5f ff f8 00.

5.1 Spatial tiles and physical order

Spatial tiles contain coding groups; they do not combine their entropy or predictor states and do not reduce the decoder to one work item per tile. Let NG be group columns, NS AC stripes, TX=ceil(NG/tile_cols) and TY=ceil(NS/tile_rows). A tile at (x,y) has stable ID y*TX+x. AC group IDs remain stripe*NG+group regardless of physical tile order. All arithmetic is checked before allocation; no permutation is sized by an ID.

Order 0 visits tile coordinates row-major. Order 1 sorts their interleaved coordinate bits (x at even positions, y at odd positions), omitting coordinates outside the rectangular tile grid. Implementations must not enumerate the padded square to find a tile on a skinny grid. The Rust rank/select implementation visits at most 32 levels. Inside each tile the coding groups are row-major. This can differ from global group raster order even under tile order 0.

Critical DATA record 65 begins a tile; critical record 67 ends it. These IDs are V4-only. Begin contains tile_id, followed, only when the exact role exists, by a length-delimited exact plan: one count per group in the tile, in that tile's group order. There are no serialized stripe counts or compressed stripe lengths in this plan. Packed width is 8*packed_block_width; packed height is 8*ceil(sum(counts)/packed_block_width); stripe count is ceil(packed_height/exact_rows). Empty exact content has no stripes. Admit counts, extents and serialized lengths before allocation.

Derive stripe ownership/count from this geometry. Each kind-57 object frames exactly one packed stripe and carries its stripe ID and model ID. Its object length bounds its entropy bytes; the common directory additionally provides its complete record extent for indexed reads. Requiring future compressed stripe lengths at tile begin would duplicate those boundaries and prevent a forward writer from publishing the tile before encoding its final exact stripe.

End contains tile_id, bytes_before_end, child_object_count, then the aggregate tile digest in integrity mode 2. Byte count starts at the begin record's first byte and includes all bytes before end, including child integrity trailers. Child count excludes begin/end and includes ignorable child objects. Every object between a tile's begin and end belongs to that one contiguous tile extent. A tile index entry covers the complete extent, including both markers, so one range read obtains all its encoded groups.

An opening tile marker cannot require the final encoded tile byte length: a forward-only writer must be able to publish a completed group before later groups arrive. The closing marker and final directory establish that length. Reader delivery before final structural validation is provisional. Seekable writers may additionally patch an admitted front-directory reservation.

DC coverage must stop at spatial tile-row boundaries. Packed exact pixels may be shared among groups inside a tile but cannot require a pixel payload in another tile. A one-tile image retains image-wide DC/exact sharing. Immutable model definitions remain separately indexed dependencies and must precede use; they never carry another group's pixels or entropy states.

A raster supplier can use explicit caller-owned tile-band reorder scratch. The codec must not hide a retained full-image raster. A spatial tile is an I/O coalescing boundary, not one decoder job or a group-completion barrier. Random-access readers may fetch the full tile once and enqueue its groups independently, including while another tile is fetched. A feed reader may publish a complete group before the tile ends; structural completion and an aggregate tile digest remain pending until close. Shared model definitions can require separate indexed reads when not already available. Smaller-group fetches remain subject to the selected directory-validation contract.

5.2 Work admission

Dimensions and counts must bound entropy output before expansion. Runs exceeding remaining samples/coefficients, arithmetic overflow and nonminimal integers are Corrupt; host capacity or caller-budget denial is TooLarge. Charge actual model/table expansion, metadata expansion, record/index visits and integrity work as well as reconstructed samples. A crop's budget includes its complete DC/exact/model dependency closure and concurrently retained state, not only its returned pixels. New IDs are keys, never allocation sizes.

No file-level speed hint overrides admission. Cooperative cancellation and implementation accounting provide operational limits; the wire makes no hardware-independent elapsed-time promise. Large canvases with bounded requested work remain valid; implementations may deny them under explicit caller limits.

6. One index schema, including model definitions

V4 has one directory body and one common placement prefix, immediately after immutable setup. All values in this prefix are canonical uvarints:

PlacementFollowing fields
0 noneNo directory or reservation.
1 tailDirectory is the final uIDX chunk.
2 frontcapacity, then exactly capacity reserved bytes containing index_len, index_body, then zero padding.

None and tail each cost one byte. Front capacity includes the encoded index_len integer, body and padding, and must be positive. The index body is identical for front/tail placement. No model-head record, fixed-slot entry width or legacy reservation state participates. An unknown placement is Unsupported before pixels. Capacity, active length, input/work and actual allocation are admitted before use. Integers remain minimal even when a growing index length needs another byte inside its slot.

A front slot with index_len zero is an unfinished seekable reservation, not a validated finalized index. Its object-stream start is already determined by capacity; the writer patches the final minimal length/body/zero padding within that same extent. Final completion requires a nonempty checked directory. A front index that cannot fit its declared reservation fails finalization; it is not silently discarded. A forward-only writer selects tail and spools entries to caller-owned scratch. Completed units never wait for the final directory.

A payload has at most one directory. None forbids a directory chunk; tail requires one at the actual file end with the V3 locator/chunk validation rules; front forbids a trailing directory. Readers never combine competing indexes. Front placement preserves sparse access for embedded/DATA-only planes and containers whose footer occupies the end. Numeric nested-plane definitions carry no placement/index of their own.

For every open DATA chunk, the end marker of the last geometry-declared tile ends DATA. A forward reader can therefore return to outer chunk framing without reading ahead for another object. No objects may follow that marker inside open DATA. A present directory must end at that same marker. Bounded DATA uses its checked declared/indexed extent, including any permitted ignorable objects after its last tile. Completing the last group does not finalize its tile or the image: trailing integrity and metadata still apply.

The index has entry_count, then entries in increasing physical offset order:


kind             uvarint   0 main unit, 1 payload-lifetime model,
                          2 tile begin, 3 tile end, 4 ignorable object,
                          5 next-main model
plane_role       uvarint   0..3; zero for tile/ignorable objects
id               uvarint   unit/model/tile ID; zero-based global ordinal
                          among ignorable objects
record_len       uvarint   complete framed length, including integrity trailer

Both placements append objects_len:u64 after entries. It counts only the framed object stream, excluding setup and placement/reservation. The trailing chunk then appends the existing chunk_len:u64 and uIDX end-locator tag; front index_body has no locator or padding. This objects_len is deliberately not V3's whole-DATA data_len. The actual DATA extent must independently agree with its setup/placement plus this object extent. Offsets are prefix sums from the first object after setup/placement/reservation. Entries cover every object exactly once, including tile markers and ignorable objects; there are no unaccounted byte gaps. Count, extent, overlap, duplicate keys and expected geometry are checked before use. A fetched record's kind, role, ID and length must agree with its entry. The existing DATA extent/chunk-locator validation remains required: a matching tail tag alone is not proof of an index. Begin/end entries determine each contiguous tile extent. Unit keys include their tile ID; model keys remain (model, plane_role, model_id). Exact stripe IDs are local to their tile.

The directory is authoritative for indexed boundaries and identity. A forward reader can walk framed objects before the tail arrives, but must reconcile its complete observed entry stream before validated file completion. Caller-owned scratch is allowed; no count-sized in-memory observation vector is required.

Model entry kinds 1 and 5 share the same (plane_role, model_id) namespace; changing lifetime never permits ID reuse. Their codes each occupy one byte, so the distinction adds no field or byte to an entry. Kind 5 binds to the immediately following main entry, across intervening definitions, ignorable objects and tile markers. Only one such binding may be pending globally; the following main must have the definition's role. Its encoded model selector must choose that model. A fetched definition's lifetime and target ID must match its directory kind and derived next-main identity. Root 0 always uses payload lifetime and precedes every main. A definition must have a later main before image completion.

This metadata lets a sparse reader locate and enforce a next-main binding without reading unrelated definition headers or prior unit prefixes/entropy. It does not prove unfetched definition bodies agree with the directory; full physical reconciliation retains that separate obligation. Unreleased V4 prototypes that labelled transient definitions as kind 1 must be regenerated.

An indexed query validates the complete directory structure, identity and tile schedule, then the prefixes/integrity of fetched objects and their dependencies. This is fetched-object validation, not validation of unread bodies. Prefix sums alone do not establish that unread physical prefixes match the directory. Full structural validation additionally reconciles every physical prefix; full pixel validation decodes all required entropy. APIs expose that scope. No V2/V3 hint-validation contract is redefined.

An ROI can locate (model, AC, 17) directly. It reads the definition record, not an earlier AC unit prefix or entropy. It also verifies the definition precedes the dependent unit and checks transient target/lifetime rules. Checksum coverage can require additional encoded bytes; that does not make the earlier entropy a decode dependency.

Numeric-only lossless DATA retains its V3 head and stripe arithmetic. Its main records use role 0 and stripe-major plane-local unit IDs; its V4 index uses this same schema and common placement. Legacy head records 10, 12 and 37 are invalid; no index control is hidden inside the numeric model head. A standalone lossless main body is unit_id followed by the existing stripe bytes; its head supplies the fixed root model. This proposal does not introduce standalone lossless local model switching or change Quick's algorithms.

6.1 Object and spatial-tile integrity

Modes 1 and 2 append exactly 16 XXH3-128 bytes to every framed model, unit, tile marker and ignorable object. Record length includes the trailer; the hash covers the encoded tag/length and body, excluding its own trailer. Bytes use the existing canonical little-endian digest representation. Mode 0 adds none.

Object hash input is IMI/v4/object, a zero byte, the 16-byte setup context, then the exact encoded prefix/body. The context is XXH3-128 of IMI/v4/setup, a zero byte, and the canonical image interpretation/coding setup. Mutable front reservations, directory offsets, locators and padding are excluded; patching them cannot invalidate previously emitted object digests. All routes use the same production context serializer.

The canonical stored-sample interpretation prefix consists of uvarints in this order: width, height, coding (0 numeric/Quick, 1 lossy), channel code, sample code, CICP primaries, transfer, matrix, full-range (0/1), alpha interpretation, and four effective significant-bit depths in memory-channel order (unused slots zero). Then lossy coding alone appends color code 0 XYB or 1 YCoCg. Append the immutable setup byte length as a uvarint and its bytes. Effective depths normalize an absent/full-width declaration to the same storage width. The domain-separated setup hash covers that complete prefix and setup. Container metadata that does not affect stored-sample reconstruction, such as orientation or an ICC profile, is outside this object context and retains its separate container-integrity policy.

Mode 2 additionally hashes each tile's bytes from begin through its final child, including their object digests. The input prefix is IMI/v4/tile, a zero byte and the setup context; append the canonical end fields tile_id, bytes_before_end, child_object_count before finalizing. Store that aggregate in the end body before the end object's own digest. The end object is not recursively included in its aggregate.

Both scopes can be computed as groups are published; no upfront checksum list or final tile byte length is required. Verified output may buffer/spool one admitted encoded object until its trailer arrives. Earlier rows are provisional until their required dependencies/scope validate. A tile digest alone cannot verify a crop without the other tile bytes; local object checks remain available. Hashing and integrity bytes consume request budgets. XXH3 is corruption detection, not authentication or a substitute for framing validation. Optional canonical decoded-group digests are a distinct, separately declared scope.

7. Decoder structure and resource contract

Each version parser produces the same checked descriptions: image setup, numeric interpretations, immutable model handles, and group work. Before a group's entropy loop, resolve its rectangle, partition/plane plans, quantizer codes and model handles once. Whole-image, row/feed and ROI drivers use that description. A live reader does this as each group arrives, not by constructing an image-wide decoded plan or waiting for the tail index.

Admit serialized bytes, counts, decoded model tables, retained definitions, current work and output before allocation. A payload-lifetime definition may be kept compressed and expanded lazily within the same cumulative budget. Expiring a transient permits reclamation; it never permits ID reuse. Sparse IDs are map keys. Model sharing never authorizes unbounded retained memory.

IMI format, version 3 (draft)

Version 4 is the current format. This reference describes the earlier framing and the sample, transform, quantizer and entropy rules shared with V4. The archived V3 prototype records the scoped defaults and model-reference experiments.

The baseline decoder supports lossless U8, U16 and F16 samples. The reference decoder enables signed integers and 32- or 64-bit samples with the extended Cargo feature. Optional CICP metadata signals display color. The format is built for fast decoding on wide SIMD (16 lanes of 32-bit state map to one AVX-512 register or two AVX2 registers), for multi-threaded decoding (stripes are independent), and for better compression than QOI on photos, screenshots and graphics.

This document describes the bitstream as implemented in imij/src/parse/, imij/src/v1.rs, imij/src/rans.rs, imij/src/tokens.rs and imij/src/mapping.rs; the lossy payload's semantics are in docs/LOSSY.md.

Readers retain version 2 semantics and translate its record ids; two legacy digest forms remain valid only in version 2. Appendix V3 gives the complete mapping and compatibility rules. Version 3 does not change reconstructed pixels.

Version 2 (2026-10-10). 0. Primitives, features and profiles

All multi-byte integers are little-endian. varint is LEB128 (7 bits per byte, high bit = continuation), at most 10 bytes. A varint must use the minimal encoding: a varint of more than one byte whose last byte is zero is corrupt, so every value has exactly one encoding. Values are unsigned 64-bit; a decoder that cannot hold a length in memory reports a resource limit, never a truncated value. f32 is IEEE binary32. Fixed-width integers appear only where a reader starts from the end of the file (the plane locator, the trailing unit index's footer) or where a writer overwrites bytes in place (the unit table reservation; both 2.7). Bit streams are LSB-first.

The 64-bit cap limits no extension point. The feature mask (1.0), which gains a bit with every feature, is a bit string of any length. Presence masks name fixed fields (the header's, the payload heads', fRAM's); new syntax goes into the record lists, whose ids are 64-bit.

0.1 Features

A feature is one critical capability: anything a decoder may lack. A header's feature set is its feature mask (1.0) plus the features its own fields imply: lossy when coding is 1 or 2, samples_32 when sample is 3-5 or 8-10 (64-bit samples code two 32-bit words, 2.1). Implied features cost no mask bit in the header whose fields imply them; a file declares every other feature it uses in the mask. The outer header's feature set is the complete admission check: a decoder that implements every feature in it decodes the file with all its frames and pages, and one that does not fails with Unsupported (naming the feature) right after the header, before reading any chunk or payload, so files that use nothing new stay readable by simpler decoders.

Channel layouts 5–8 require pixel_models and lossless/numeric coding. The layout identity is not a channel count: CMYK and OklabAlpha have four stored slots; Oklab has three. The bits are ordered by how often the reference encoder writes the field, so common files keep present in one byte. A sample type 6-10 in a file whose mask lacks its feature is Corrupt. coding 1-2 implies the feature lossy and sample 3-5 and 8-10 the feature samples_32: they join the mask in the header's feature set (0.1) without a mask bit.

Feature mask encoding. The mask is a little-endian LEB128 bit string of any length: each byte carries the next 7 bits (byte k holds feature ids 7k to 7k + 6 in bits 0-6), bit 7 set means another byte follows. Masks below 2^64 are therefore exactly the varint of the same value; only a mask with a feature id of 64 or more goes past a varint's range (a tenth byte above 1, or more than ten bytes). The varint rules hold except the 10-byte limit: the last byte is nonzero unless it is the only byte (minimal encoding; otherwise Corrupt), and the mask ends inside the header (header_len bounds it; running past it is Corrupt). A decoder reads it in one pass and needs to store only the ids it knows: any set bit at an id it does not implement is Unsupported (0.1), at whatever byte it sits.

Two ways to write the same header. The *full* form sets every bit (present = 0x1FF, varint bytes FF 03) and writes every field, the feature mask included (0 when there are none): it reads without the defaults table. The *masked* form sets only the bits of fields that differ from their defaults; encoders write it, and the header of an 8-bit sRGB RGB lossless image is four bytes: 02 00 width height. Decoders accept any mask, including fields written with their default value, and both forms decode to the same image description. Examples (masked): lossy YCoCg RGBA 64 x 32 is 02 09 02 04 40 20 (present = coding | channels; then coding 2, channels 4, width, height); a lossy file with seed tables and exact blocks declares features = 3 in one byte (02 05 03 01 ... for XYB RGB).

Internal representation. Lossless coding stores the samples exactly: integer prediction with a per-stripe reversible residual decorrelation (section 2); the samples themselves are never color-transformed. Lossy coding converts to three f32 planes in the named internal color space (XYB: Y, X, B - Y; YCoCg: float Y, Co, Cg, not the integer YCoCg-R lifting) before the transform, and the decoder converts back to the output format the header describes. The header's coding is the only statement of the lossy color; the payload does not repeat it. Lossy coding takes u8, u16, u32, f16 and f32 samples; signed integer (i8, i16, i32) and 64-bit samples are lossless only, and a lossy file with such a sample type is corrupt.

Evolving the header. New fixed fields take new presence bits; their absence keeps today's meaning. Everything else goes into the header record list (id, len, payload; section 1). Versions 2 and 3 define two records, both ignorable: id 2, the file checksum record (1.4), and id 4, the DATA locator (below). Ids 1 and 3 held version 1's required-profiles record and mixed-pages capability; they are retired, so a file carrying them is Unsupported like any unknown critical record. Writers keep the records in increasing id order when they add one to a finished file. Changing a default requires a new header version, which older readers reject.

V4 additionally defines ignorable header record 6 for reconstructed floating-point guarantees.

DATA locator (record 4, even: ignorable). Written by writers that know every byte up to the end of DATA's head before they write the header (writers buffer up to the start of DATA; metadata such as ICC, Exif and XMP stays before DATA, where a streaming decoder needs it):


prefix       varint    bytes from the DATA chunk's tag to the end of its
                       head (2, 2.8: through the head's record list and,
                       lossy, its nested heads), where the first unit
                       record starts
count        varint    chunks between the header and DATA
lengths      count x varint: each chunk's whole length (tag, length varint,
                       payload), in file order

The chunks start right after the header; DATA starts after the last one. A reader that uses the locator first checks it against the file: every listed chunk's header (fetched in one batch with the DATA prefix) must have a valid tag that is not DATA or an unknown critical tag, a length field that makes the chunk exactly its listed length, and the chunk after them must be DATA with a head that ends exactly at prefix. When anything disagrees (a stale locator after an editor changed the chunks, or any other mismatch), the reader ignores the locator and walks the chunks. The reference writers write a locator only when DATA's head carries the unit table hint or a unit table reservation (head records 10 and 12, 2.7). Writers rewrite the locator whenever they change the chunks before DATA. A cSUM chunk before DATA (1.4) is listed like any other; the checksum covers the locator, so a writer settles the locator (with the chunk's length, which follows from the covered length) before it computes the digests. Nested files (frames and pages after the first, previews, plane tiles, the gain map image) carry none: their reader already holds their bytes.

1.1.1 Historical color origin (cORg)

An optional ancillary, safe-to-copy record describes the original source color independently of the current header CICP and active iCCP. It never affects pixel reconstruction or current color authority. Editors may retain it after converting pixels, while updating current color information separately.

Version 1 payload, in order:

  • Version byte 1.
  • Provenance byte: 0 assumed, 1 ICC, 2 CICP, 3 legacy gAMA/cHRM.
  • Historical authority byte: 0 ICC, 1 CICP.
  • Presence flags: canonical unsigned varint, bit 0 ICC, bit 1 CICP.
  • If CICP is present: four bytes (primaries, transfer, matrix, full range 0/1).
  • If ICC is present: all remaining payload bytes, unchanged. An empty present

    • profile is distinct from absence; this record does not validate ICC contents.

No other trailing bytes are permitted. Typed origin readers reject duplicates, truncation, nonboolean range or trailing data as Corrupt; unknown versions, provenance, authority or flag bits return Unsupported. Pixel readers may ignore this optional record, as with kVAL. Declared historical authority is not a requirement for a carrier to exist: assumed and legacy origins can have neither carrier. No deprecated gamma/chromaticity values are encoded here.

The API uses zenpixels::ColorOrigin. PNG import records cICP over ICC without activating the superseded ICC. Named sRGB uses its equivalent CICP origin; legacy normalization and absent descriptions remain distinguishable. PNG export uses only active color and omits this historical record and its carriers.

Unified sequence items (kind 4, feature sequence_items)

Kind 4 uses the same aNIM fields, followed by one presentation byte: 0 = pages, 1 = animation; other values are Unsupported. No trailing bytes. Feature 19 is required even for a single item and applies to primary-only readers. The first item is DATA; later items are complete nested images in fRAM with x0 = y0 = 0, no previous/empty bits, and an optional record list. Each item has its own complete pixel description, color, orientation and metadata. Nothing is inherited from another item. Animation items have identical ImageInfo (geometry, sample/channel layout, significant bits, CICP and alpha mode); pages may differ. Timing is the same rational grammar for both.

A missing reference record means an independent keyframe. Critical frame record 111 (33 under header version 2) contains a minimal varint zero-based earlier-item ordinal followed by that item's canonical decoded-raster digest defined by pSUM (1.4.1), using its own ordinal: a digest algorithm id (1.4.2) and that algorithm's result bytes in the order defined in 1.4.2, or, under header version 2 only, exactly eight bytes without an id (XXH3-64; files written before 2026-10-25). An unknown id is Unsupported. Forward/self references, incompatible ImageInfo, malformed controls and undeclared features are Corrupt at constructor admission. The reference is a complete reconstructed raster, not the original source before lossy or near-lossless coding. Its hash is verified before overwriting any output. This is accidental wrong-reference detection, not cryptographic authentication.

The nested image uses the existing inter reconstruction when a reference is present; its full dimensions replace the rectangle convention of kinds 1–3. Lossless inter predictors remain limited to their existing supported slots; near-lossless images remain intra. Lossy keep blocks use the current item's own color interpretation. Both presentations use the same renderer. An encoder may choose intra instead of a supplied candidate and may impose a keyframe interval. Page defaults are independent. Clients control which earlier rasters to retain or fetch; imij-set may cache seek/dependency summaries, but the IMI file is authoritative for references and rendering.

kVAL carries optional typed metadata on an ordinary V4 image or any sequence item. V2/V3 use the legacy FourCC kVMD for the same payload. V4 readers also accept that spelling for earlier V4 files. Both spellings share one per-image slot. The payload starts with version byte 1 or 2, then the attribute map: filename flag 0/1, optional length-prefixed UTF-8 filename, attribute count varint, then ordered unique nonempty UTF-8 keys, type byte and value. Types are 0=text and 1=bytes (length-prefixed), 2=u64 LE, 3=i64 LE, 4=finite IEEE f64 LE, 5=boolean byte 0/1. Keys are at most 128 bytes, filename at most 4096 bytes, and there are at most 64 attributes. Names exclude NUL. Empty metadata may have an empty representation following the version. Pixel readers may ignore this ancillary record; attribute readers reject malformed/duplicate chunks and report unknown versions as Unsupported.

Version 1 has the imij-set entry-metadata body's 16,384-byte ceiling, excluding the version byte. Version 2 uses the same map grammar with the image reader's metadata admission policy. The reference image attribute API defaults to 16 MiB including the version byte and allows an explicit caller byte limit. Aggregate decode and validation metadata budgets also apply. Writers use v1 when the body fits 16,384 bytes and v2 for larger maps. Archive entry metadata remains a separately bounded caller-supplied summary.

A positional item reader can skip attribute values by their wire lengths and locate a selected value for a later read. It can also select an sMDT record by schema ID and instance key before reading the packed body. This walk stops at DATA. A complete validator reads the bodies and checks the enclosing integrity policy.

An optional checksum of the file in fixed-size pieces, so decoders verify it in parallel or as bytes stream in, and a decoder can check it with container parsing alone.     • (tag, length and payload) removed: the signature, header_len, the header and every other chunk, nested files included. They are cut into 2^k-byte pieces, the last one short. Offsets do not depend on where the chunk sits, so it may move between chunks without changing.

  • Header record. A file with a cSUM chunk carries header record 2

    • (even, ignorable): id 2, then a payload of k and the algorithm id (length 2). It tells a streaming reader the piece size and the algorithm before the table arrives and tells a reader that a table must be present: a file with the record and no table (a stripped or truncated trailer), a table without the record, or a table whose k or algorithm id differs from the record's is corrupt (whether or not the reader knows the algorithm), as is a record whose k is outside 10 ..= 40. Under header version 2 only, a length-1 payload of k alone (written before 2026-10-25) names no algorithm: it admits a table of algorithm 0 or of an algorithm the reader does not know (skipped, 1.4.2); a table of another known algorithm is corrupt. Older readers skip the record and the chunk.

  • Placement. Anywhere among the chunks, at most once (a second one is

    • corrupt). Writers that hold the file in memory put it just before DATA (this library does), so a streaming reader can check each piece before it decodes bytes from it. A writer that streams puts it last, or just before a trailing unit index (2.7), which stays the last chunk; readers then check pieces as bytes arrive and report a mismatch when the table arrives. An open DATA chunk (length 0) changes nothing: its bytes are covered like any other, and a table after it is found once DATA ends.

  • Validation. A width the algorithm does not allow, k outside 10 ..= 40,

    • covered_len 0 or different from the file length minus the chunk, or a digest count other than ceil(covered_len / 2^k) is corrupt. Another algo byte: the chunk is skipped (not checked); the record and placement rules still apply.

  • Verification. A mismatching piece is corrupt (`file checksum

    • mismatch`). The reference decoder verifies by default (Limits::verify_checksum; PlaneSetLimits::with_checksum_verification); turned off, it reads the file as a decoder without checksums would. Verifying, it checks the header record with the header (a malformed record is reported before the chunks are read, whether or not a table follows). When the table comes before the failing bytes, a mismatch explains any other error: when a chunk rule, parsing or decoding fails before the pieces under the bytes read so far were checked, it checks them and reports the mismatch in its place (the std::io::Read decoder reads on to the end of the piece; rows it already delivered stay delivered). When the table comes after them, the error stands: a decoder does not read on to the table to explain it. Slice decoders check every piece before the first pixel. A multi-threaded decode checks them on its workers: lossy before decoding, lossless before each unit the pieces under that unit's bytes, reporting a mismatch after the output was written. StreamDecoder checks each stripe's pieces just before its first row. The std::io::Read decoder hashes pieces as bytes arrive; when the table came first it reads each piece of up to 4 MiB ahead and checks it before decoding from it (a larger piece is checked when it ends), and it compares a trailing table when the table arrives, after the rows. previews checks the pieces wholly before DATA when the table precedes them; header checks nothing. The region reader checks every piece under a byte it uses before decoding from it: each fetch is rounded out to whole pieces, and the table and the pieces under what opening read come with the first region (a table after DATA is found by reading the chunk headers after it). It charges the table and the pieces to the region's byte limit with the records, before it fetches: a region whose records and table exceed the limit is TooLarge, and pieces that do not fit with them are hashed through a buffer within the limit (at most 1 MiB), so a file's piece size never makes a small region read or allocate more than its limit.

  • Nested files. Frames and pages after the first, previews and gain

    • map images are complete files and may carry a cSUM chunk (and header record) of their own; this library's writers put none in them, and the outer file's table covers their bytes. A decoder that verifies checks the table of every complete file it parses, whether or not the outer file has one (the reference FrameDecoder checks a frame's or page's own table when it reaches it); one that does not verify skips nested and outer tables alike. Plane tiles admit only DATA, so they carry none.

  • Named planes. In a plane set the chunk sits in the primary, before

    • its DATA chunk, and covers the whole plane set. The records, the pIDX index and the sLOC locator keep their layout (records from the primary's end to the index, the locator right after the index, its file_len counting the whole file), so plane readers without checksums read such files. When the header record announces a table, the indexed reader finds it through the primary's chunk framing and checks the pieces wholly inside each range it fetches, or with round-out every piece a fetch overlaps (PlaneSetLimits::with_checksum_round_out).

  • Reserved unit tables. The pieces cover the DATA head, a unit table

    • reservation (2.7) included. A writer that fills the reservation in place fills it first and then computes the digests of the pieces under it (or recomputes them); the trailing unit index is covered like any chunk.

  • Choosing k. One piece covers files up to 64 KiB; files up to 16 MiB

    • get at most 16 pieces of 64 KiB to 1 MiB, larger files 1 MiB pieces (benchmarks/csum_pieces_2026-10-07). With one piece the table is the whole-file digest.

1.4.1 Decoded bitmap checksum (pSUM)

pSUM is optional, ancillary, public and unsafe to copy after pixels change. It needs no feature bit or numeric record. It occurs at most once, bounded, before DATA; an open, duplicate or after-DATA table is Corrupt. It attests native reconstructed pixels independently of cSUM encoded bytes.


version      u8        1
algorithm    u8        digest algorithm id (1.4.2); writers default to 1
width        u8        the algorithm's digest width
reserved     varint    0 (canonical zero; no options defined)
count        varint    images, frames or pages; 1 ..= 1,000,000

For version 1 and a known algorithm, count must equal the announced aNIM count (or 1 without aNIM) and the actual fRAM count plus 1. Unknown versions or algorithms are skipped and never reported as verified; placement, uniqueness and the 128,000,014-byte payload cap (the widest algorithm) still apply. Partial ROI reads remain Pending; a full-primary read may be Verified without force-decoding anything beyond the requested rectangle. Checking compressed pieces alone never establishes decoded bitmap verification.

add_pixel_checksum is an explicit encoder finalizer, off by default: existing encoder output bytes are unchanged. It reconstructs still images row by row and animations/pages in a reusable fallibly allocated buffer. Standalone inter-frame updates without reference context, existing pSUM and indexed plane-set remux are refused. Known cSUM is verified, then recomputed after insertion and locator settling; unknown encoded checksum algorithms are refused. Seal a plane primary before constructing its indexes, and seal preview/gain-map files before embedding. Metadata-only compression retains the exact table because bitmap layout and pixels remain unchanged. Parsed Metadata never exports pSUM as an opaque chunk; encoders reserve the tag against stale caller injection. Pixel-changing editors must recompute or explicitly drop the unsafe-to-copy checksum.

This is accidental-error and decoder-parity detection, not authentication. An encoder using the shared reference decoder catches independent decoder agreement failures; it cannot detect a common-mode error in that shared pipeline. Algorithm reference: xxHash.

1.5 Science records (cALB, aXES, cORD, sMDT, cATG)

Five ancillary, public, unsafe-to-copy chunks say what stored samples mean: how they map to a physical quantity or to named categories, which of them are missing, where they sit in a physical coordinate space, and the domain metadata they came with. They never change decoding: a decoder that does not know them skips them (1.1) and decodes the same samples, so they need no profile. They are unsafe to copy because they describe the samples and the geometry: an editor that changes the pixels must drop them. The guide with mappings from FITS, CF/netCDF, OME-Zarr, DICOM and GeoTIFF is docs/SCIENCE_METADATA.md.

The records describe the file's image. Under aNIM kind 4, the outer image is item 0 and each nested item can carry its own science records, including sMDT in CBOR or JSON, cALB and cATG. A reference supplies pixels only. Each item uses its own records with zero cross-item inheritance. Legacy aNIM kinds 1–2 use the outer science records. In kind 3, mixed pages have their own science records, with the outer image supplying page 0. Preview, gain-map and plane-tile children do not carry these chunks. Plane sets keep per-plane records in one attachment (below).

cALB, aXES, cORD and cATG occur at most once per image or item. sMDT occurs at most 64 times with distinct pairs of schema ID and optional instance key. Writers place these records before the image's DATA.

Encoding. Integers are little-endian, varint is LEB128 (section 0), zigzag is a varint z holding the signed value (z >> 1) ^ -(z & 1), f64 is IEEE binary64, and str is a varint byte length followed by that many bytes of UTF-8 containing no NUL. Every payload starts with version u8. All records define version 1. cALB and sMDT also define version 2 below.

Unknown versus malformed. A reader skips a record whose version it does not know, an sMDT whose format it does not know, and a cORD whose aXES it skipped. Any other violation of the grammar or the rules below (truncation, trailing bytes, a reserved flag bit set, a value out of range, a repeated record) makes the record malformed. Malformed records never fail an image decode; a reader of the records reports them (the reference library returns Corrupt from ScienceRecords::from_metadata).

Stored values. A stored value is a sample as the decoder outputs it (after the channel maps, 2.1). cALB compares and scales it as a binary64 number. That conversion is exact for integer samples of up to 32 bits and for every float type, but not for 64-bit integer samples (u64, i64, where a profile defines them) whose magnitude exceeds 2^53: for those, a nodata value or a valid-range bound also matches the neighbouring stored values that round to the same binary64, and the physical value is rounded. cALB v2 can test integer sentinels in their exact stored domain. Scaling and valid-range bounds still use binary64. cATG compares integer samples as integers (below).

2.1 Channel maps

The *coded channels* are the image's channels, except that a 64-bit sample type (Extended 0.2) codes each channel as two 32-bit words: with C channels, coded channel c is the hi word of channel c and coded channel C + c its lo word. The DATA head has one map per coded channel, in coded channel order. Each coded channel is coded with bits significant bits (0..=container depth D, where D = 8 for u8/i8, 16 for u16/f16/i16 and 32 for u32/i32/f32 and for the words of u64/i64/f64). The decoder expands a coded value s to the container sample (or word) x:

modenameexpansion
0Lsbx = s
1Shiftx = s << (D - bits)
2Replicates bit-replicated to D bits (`s<<(D-n) \s>>(2n-D) ...`)

For 32-bit coded words, Replicate and Scale are allowed with bits <= 16 (e.g. 8-bit data stored as v * 0x01010101). Any other mode is Corrupt (closed, 0.3).

Validity. bits <= D for every map, and per mode (anything else is Corrupt): Lsb any bits; Shift bits >= 1; Replicate and Scale bits >= 1 (and <= 16 for 32-bit words); Const only for alpha and the lo word of a 64-bit channel; F16InF32 only for f32 samples, bits = 16; UnormF32 only for f32 samples, bits 1..=16; Offset only for 32- and 64-bit samples; FloatShift only for f16 and f32 samples, bits 1..=D - 1. value is read for every map and used only by Const and Offset (writers write 0 for the others).

Const values are order-domain values. The expansions above produce the order-mapped sample o (below), and Const's value is such an o: a decoder applies the order map inverse to it as to any expanded value. For an f16 channel, value = 0x3C00 outputs 1.0 (non-negative halves map to themselves) and value = 0x8000 outputs the half 0xFFFF.

This is how 10- and 12-bit content in 16-bit containers costs no more than its real precision whether it is MSB-aligned (Shift), bit-replicated (Replicate), range-scaled (Scale) or LSB-aligned (Lsb with bits < 16), and how 0/max alpha codes as a 1-bit channel. The encoder picks the smallest bits whose mapping reproduces every sample exactly.

Samples are first mapped to order-preserving unsigned integers (each an involution); maps apply to the result o:

  • f16: o = v ^ ((v >> 15) * 0x7FFF)
  • f32: o = v ^ ((v >> 31) * 0x7FFF_FFFF) (float maps 5 and 6 are defined on

    • the float and then mapped)

  • i8: o = v ^ 0x80; i16: o = v ^ 0x8000; i32: o = v ^ 0x8000_0000
  • u8, u16, u32: o = v
  • u64, i64, f64: the sample v splits into its hi word h = v >> 32 and

    • lo word l = v mod 2^32. The hi word maps like a 32-bit sample of the same kind (u64: h; i64: h ^ 0x8000_0000; f64: the f32 map on h); the lo word is coded as is (o = l). Float maps 5 and 6 do not apply to either word.

The lo word is not order-mapped so that zero low bits stay zero whatever the sign: f64 samples widened from f32 code a 3-bit lo word under a Shift map for negative samples too. Prediction treats the two words as independent 32-bit channels (Sample types discusses and measures the cost).

FloatShift (map 8) codes floats whose low D - n raw bits are zero in every sample (BitRound, GDAL DISCARD_LSB) at n bits whatever their signs. order_D is the float order map above (f16 for D = 16, f32 for 32) and order_n(t) = t ^ ((t >> (n - 1)) * (2^(n-1) - 1)) is the same map on an n-bit sign-magnitude pattern; both are involutions. So s is the top n raw bits ordered as an n-bit float, the decoder's sample (after the order map inverse of step 4) is exactly order_n(s) << (D - n), and NaN payloads, signed zeros, infinities and subnormals round-trip bit for bit. Shift on ordered values cannot do this for negative samples: the order map turns their zero low bits into ones. Prediction, contexts and tokens see s as any n-bit slot (residuals modulo 2^n, so -0 sits next to +0). Map 8 is gated syntax of feature float_shift (0.1): in a file that does not declare it, map 8 is corrupt. Map 7 likewise needs offset_map.

Value tables (map 9) code a channel that uses few of its container's values, whatever their pattern: each sample codes the index of its value among the values the channel uses. The map's value is the table's entry count minus one; the table T follows the map's value field in the head:


T[0]         varint    t0: T[0] = t0
T[i], i > 0  varint    ti: T[i] = T[i-1] + 1 + ti

so the entries are strictly increasing ordered values o. A table has 1..=65536 entries and no more than 2^D; each entry is below 2^D (else Corrupt), and bits is the fewest bits that index every entry, ceil(log2(value + 1)) (0 for one entry; any other bits is Corrupt). A coded value s expands to T[min(s, value)]: indices past the last entry expand to the last entry, so every coded value has a sample. As for the other maps, the order map inverse then gives the sample (64-bit samples: per word, as above). The reduction an inter frame applies to its reference (reduce, section 4) is the index of the greatest entry at most o, or 0 when o < T[0]: exact for every value in the table and defined for every other. Map 9 is gated syntax of feature value_tables (0.1). Near-lossless bounds do not apply to it (2.6), and the nested heads of a lossy payload do not have it (2.8).

Value tables generalize the regular maps: Shift, Replicate, Scale and FloatShift each describe one regular sparse set of values, a table any. Half floats from tone-mapping inverses and network outputs, and single floats decoded from Radiance RGBE files, use a few hundred to a few thousand distinct values per channel; their indices predict like a smooth image (value-table study).

2.2 Slots

The coded channels form slots in this order:

  • Gray, GrayAlpha: [Y] then alpha unless its map is Const.
  • RGB, RGBA: [G, R, B] then alpha unless its map is Const.
  • CMYK: [C, M, Y, K], all four ordinary color slots.
  • Oklab, OklabAlpha: [L, a, b] then alpha unless its map is Const.
  • Scalar: one numeric component with no color transform or alpha.
  • 64-bit samples: the slots of the hi words in the order above, then those

    • of the lo words in the same order, each unless its map is Const (at most eight slots). The color slots are the hi words: RGB decorrelation (2.4) uses their first three slots; cross context (3.1) uses each model's color slots and never the lo words.

Slot s has depth n_s = bits of its channel. Color decorrelation (2.4) is allowed only for RGB/RGBA when the three color slots have equal depth. CMYK and Oklab use decorrelation mode 0; the cross context may still reference the first color slot from any later color slot (including CMYK K).

2.3 Stripes and lanes

Rows are split into stripes of H rows (the last may be shorter). Stripes share nothing but the models: no prediction, context or entropy state crosses a stripe boundary, so stripes decode in parallel.

With G > 0 each stripe is further split into NG = ceil(width / G) column groups: group g covers columns [g*G, min((g+1)*G, width)). A group is coded exactly like a stripe of an image as wide as the group (its own decorrelation mode, row predictors, lanes and streams); groups share only the models. Nothing crosses a group boundary, so the groups of a stripe decode in parallel, and a column range needs only its groups. With G = 0 there is one group, the whole width.

Each group is split into L lanes of columns. With group width gw, lane width lw = ceil(gw / L); lane l covers the group's columns [l*lw, min((l+1)*lw, gw)) and may be empty. Active lanes are the non-empty prefix. Within a lane, positions are visited in *lane order*: row by row, left to right. A *step* is the pair (row, lane-local column x); all lanes advance through steps together.

Neighbors and contexts are lane-local: the left neighbor of lane column 0 is not the previous lane's last column.

Nested lossless images inside a lossy file (DC, alpha) use the column groups the lossy payload prescribes (docs/LOSSY.md): none without lossy groups, else G / 8 (DC image) and G (alpha image).

2.6 Near-lossless images (feature near_lossless)

A payload whose head carries record 19 codes some channels near-lossless: closed-loop residual quantization in the predictive path above, as in JPEG-LS NEAR. The record is gated syntax of feature near_lossless (0.1): in a file that does not declare it, it is corrupt. Its payload is one varint bound δ per channel (container channel order), in coded units of that channel, and nothing else. Bounds are defined for u8, u16, u32 and i32 samples only; with any other sample type (floats, i8, i16, 64-bit) the record is corrupt.

  • δ = 0: the channel is coded exactly (sections 3-4 unchanged).
  • δ > 0 requires a coded channel whose map is neither Const nor Table

    • (map 9: its indices have no uniform step) and δ <= 2^(n-1) - 1 for its coded depth n (so channels of at most 1 bit are exact). At least one channel has δ > 0. Anything else is corrupt. A slot has the bound of its channel.

  • Payloads with bounds never use predictors 7..=9 (section 4); a frame may

    • still keep the previous canvas outside its rectangle.

  • Palette stripes (2.5) code exact values; bounds do not apply to them.
  • Nested DC, alpha and exact-block images of lossy payloads carry neither

    • record 19 nor maps 8 and 9 (a decoder rejects any there as corrupt, 2.8).

Decoding. Entropy decoding and decorrelation (section 4 steps 1 and 2, modulo 2^n) are unchanged. In step 3, a slot with δ > 0 reads its residual d as the quantized residual q = sext_n(d) (d as an n-bit two's-complement value) and reconstructs


v = clamp(pred + q * (2δ + 1), 0, 2^n - 1)

in exact integer arithmetic instead of (pred + d) mod 2^n; prediction reads reconstructed values as always. 64-bit signed arithmetic suffices (|q| <= 2^(n-1), 2δ + 1 < 2^n). Because 0 <= pred <= 2^n - 1, any product of magnitude at least 2^n clamps to an end of the range, so a SIMD decoder may saturate |q| (2δ + 1) at 2^n (or at its lane maximum) without changing the result. Step 4 (channel maps) is unchanged.

Bound. An encoder that predicts from the values a decoder reconstructs, and codes q = sign(e) * floor((|e| + δ) / (2δ + 1)) for e = x - pred (x the source coded value), gets |v - x| <= δ for every sample: q is `e / (2δ + 1)` rounded to nearest (an odd step has no ties), and the clamp only moves v toward [0, 2^n - 1], which contains x. For δ >= 1, `|q| < 2^(n-1), so q mod 2^n round-trips through sext_n`. A file with bounds from such an encoder therefore states, per channel, the largest coded error of every sample (the format cannot check this; a decoder reconstructs whatever residuals it is given).

Sample units. The coded bound becomes a bound in sample units through the channel map: Lsb and Offset maps and the i32 order map preserve differences; a Shift map multiplies them by 2^(D - n); Replicate and Scale by at most the largest expansion step of δ coded steps. The reference encoder takes a bound in sample units and writes the largest coded δ whose expansion stays within it (5. Encoder notes). Float channels (f16, f32) are always exact: their coded values are order-mapped bit patterns, where an integer step has no physical meaning. Error-bounded floats go through a declared integer quantization: store the quantized integers as u16/u32/i32 samples and describe the dequantization (scale, offset) as metadata.

Parallelism and SIMD. The quantization loop runs inside each stripe and column group, which still share nothing, and the 16 lanes stay independent; the change to a vector decoder is a sign extension, a multiply and a clamp after the prediction.

Order. The head's geometry fixes which main records come, in which order. A lossless payload has one stripe record per unit, in unit order (stripe-major, then column group). Side records. Each main record may be preceded by one side record with id kind + 19 (70, 72, 74, 76, 78, 80; even, so ignorable; none is defined yet, and a reader skips it; header version 2 wrote kind - 1). A payload therefore always ends with a main record, and a forward reader of an open DATA chunk knows where it ends. New critical per-unit data gets a new odd id and a feature.

Unit table hint (head record 10, ignorable). One varint per main record, in record order: the bytes of its span, the main record plus its side record, framing included (each entry at least 2). It lets a reader find any record from one small fetch: the region reader computes every span's offset from it. Every decoder checks it: the entry count must match the head's geometry, the entries may not sum past the bytes after the head, and a reader that walks the records compares every span with its entry; any mismatch is Corrupt (unit table length, unit table exceeds DATA, unit table does not match the records). A reader that finds records through the hint instead of walking them (the reference region reader) checks it when it opens the file: every span must start with the record head of the main record the geometry expects there (after at most one side record), and that record must end where the span ends. With the sum check, this names exactly the records a walk finds, so every route reads the same records or fails. The reference reader fetches each span's first 20 bytes for this (except the bytes it already holds), in batches of 65,536 spans, plus one more batch per batch for main records that follow side records. This check is global: opening reads one record head per main record of the primary image whatever region is asked for, so its work grows with the unit count. The reader charges these bytes to its byte limit (Limits::max_bytes) before each batch and refuses an open that would pass it (TooLarge), so a caller bounds the open's work with that limit. Writers write the hint for payloads of two or more units they hold whole, and none for one unit. Nested images of a lossy payload (DC, alpha, exact) never carry a hint of their own (Corrupt in a nested head): their records are the lossy units' records. Every complete file (frames, pages, previews, plane tiles, gain map images) has its own payload and so its own records and hint.

Unit record ordinals (head record 37, critical, empty payload; feature unit_ordinals). When a lossless or lossy head carries record 37, every main unit record in its payload begins with ordinal: varint, its 0-based main-record index 0 .. R - 1, followed by the record's body. Side records (even ids) are unchanged. Record 37 in a file whose feature set lacks unit_ordinals, in a nested image head, or with a non-empty payload, is Corrupt. Walking decoders verify ordinal == i on the i-th main record (unit record ordinal on mismatch). Indexed region decoders (RegionReader) validate the unit table's entry count R and byte sum at open without reading every span's record head (unless exact-block offsets must be located), and verify ordinal == r locally on each main record r fetched for a region.

Unit table reservation (head record 12, ignorable). A writer that cannot hold the payload whole writes its head before its records, so it cannot write head record 10 there: varint entries change length with their values. Record 12 has a length the writer knows before it codes any record, so a writer that can seek back fills it in place after the records, and one that cannot marks it to say where the spans went:


state    u8     0 empty, 1 check tail, 2 filled (others: Corrupt)
state 2: width  u8      bytes per entry, 1 ..= 8 (others: Corrupt)
         spans  R x width bytes: head record 10's entries, in its order,
                each little-endian in width bytes
state 0 or 1:   zero bytes to the end of the record (any count)
  • R is the main record count the head's geometry names. A writer

    • reserves 2 + R x width bytes as state 1 and zeros, writes the records, and then writes state 2, the width and the spans over the reservation; nothing else in the file moves. A writer that cannot come back (its output turned out not to be seekable, or a span does not fit width bytes) leaves the reservation as it is and appends the trailing index.

  • Filled (state 2) is the unit table hint, with every rule of head

    • record 10 above (entries at least 2, checked by every decoder, and at open by readers that find records through it). The record is exactly 2 + R x width bytes (unit table length), checked against R before anything is allocated.

  • Empty (state 0): the writer reserved the space and wrote the spans

    • nowhere. Readers walk the records and do not look for a trailing index.

  • Check tail (state 1): the spans are in the trailing unit index

    • (below). A reservation starts in this state, so a writer that does not fill it leaves it as it is; a writer that knows from the start that it will not seek writes the record with no padding (3 bytes: id 12, length 1, state 1).

  • Padding (states 0 and 1) is zero (unit table padding). A head carries

    • at most one of records 10 and 12 (unit table twice); nested heads carry neither (Corrupt).

Trailing unit index (uIDX chunk: ancillary, public, unsafe to copy; after DATA, at most once). The spans of a payload whose head says check tail, written after the records by a writer that could not put them in the head:


spans      R varints: head record 10's entries, in its order
data_len   u64      bytes of the DATA payload it indexes (head and records)
chunk_len  u64      bytes of this chunk: tag, length field and payload
tag        4 bytes  "uIDX" (the end of the file names the chunk)
  • Found. The index counts only when the payload's head says check tail

    • and the chunk is the file's last: its tag is uIDX, its payload is at least 20 bytes, its chunk_len is its length and its last 4 bytes are uIDX. Otherwise there is no index and readers skip the chunk (after the chunk rules: at most once, never before DATA). A reader that does not walk the chunks after DATA (the region reader) finds it from the end of the file: the last 4 bytes, chunk_len before them, and at that distance from the end the chunk header. Such a reader may take the end of another chunk's payload for an index; it checks what it finds as below, so a region never decodes from a wrong span, but such a file can be Corrupt for it and not for a reader that walks the chunks. Writers never write one. A file whose index was stripped, or whose writer put another chunk after it, has no index: readers walk it, and it decodes. Only the DATA payload has a trailing index: in any other payload (a frame, a page, a preview, a plane tile), check tail means readers walk the records, and writers that hold such a payload whole write head record 10 instead.

  • Bound to its DATA by data_len, not by an offset, so editing the

    • chunks before DATA keeps it valid. data_len must be the DATA payload's length (a bounded DATA: its length field; an open one: where its records end, before the index starts), else `unit index for another DATA`.

  • Checked like head record 10 by every reader that reads it: the entry

    • count from the geometry, bounded before anything is allocated (`unit table length), each entry at least 2 (unit table entry`), the entries summing to the bytes after the head (`unit table does not match the records`), and every span against the records (readers that walk the records compare spans; the region reader checks every span's record head at open). A forged index is Corrupt on every route that reads it, and never makes a reader decode another unit's pixels.

  • One index in use. A head with check tail has no hint, and a trailing

    • index counts only with check tail, so a payload never has a head hint and a trailing index in use at once: a uIDX chunk next to a head hint (head record 10 or a filled reservation), next to an empty reservation, or with no record 12, is skipped whatever it holds and cannot change any outcome.

Where readers find the spans. In the head: head record 10 or a filled reservation. At the end of the file: check tail with a trailing index. Nowhere (readers walk the records): an empty reservation, check tail with no index found, or no record. Decoders that walk the records need none of these; they check the one that applies. The reference region reader fetches the last 64 KiB of the file for a check-tail head (and the rest of a longer index in one more batch) before it checks the spans' record heads.

Writers. The reference writers hold the payload whole and write head record 10. A writer that streams its records writes check tail and appends the index as the file's last chunk (after a streaming cSUM, 1.4). A writer that may be able to seek reserves record 12 as check tail, fills it after the records when it can, and otherwise leaves it and appends the index. Only the unit table can follow the records: the entropy models and tables in the head (2, 2.8, section 3) code every record, so a writer settles them before it writes the first record, and they cannot be filled in afterwards.

A record is exactly its len bytes. Inside it, the rANS streams of a lossless record (including the DC and alpha records of a lossy payload, which are nested lossless images) and the compact rANS payload of a lossy record may end with words their decode never reads: decoders ignore them, since a region decode that stops above a unit's last row cannot see them and a full decode must agree with it, and writers write none. A compact rANS payload is still a whole number of 16-bit words, and an exact record, parsed whole before any block decodes, must end where its record ends; otherwise the file is Corrupt for every decoder (record_slack_has_one_outcome_in_every_decoder). A record that overruns the payload, or bytes after the last record, are Corrupt.

The format puts no limit on the unit count. The reference region reader (imij::region) refuses payloads of more than 2^24 units with TooLarge (a reader limit: full decoders read them), and a head naming more units than the bytes after it is Corrupt before anything is allocated (`stripe count exceeds data`), since every unit takes at least one byte.

2.8.1 Matrix 5: jpegli's distance-dependent tables

Matrix id 5 (feature dequant_presets) computes its base tables from the file's own quant_scale, following jpegli's nonlinear distance law (jpegli; the constants are jpegli's kBaseQuantMatrixYCbCr and kFrequencyExponent, the same values as zenjpeg's BASE_QUANT_MATRIX_YCBCR and FREQUENCY_EXPONENT). Every implementation must produce the same f32 values; this section fixes the constants and the operation order.

All arithmetic is IEEE: f32 operations and f64 operations each rounded to nearest, ties to even, one operation at a time in the order written (no fused multiply-add, no reassociation). B_c[i], F and e[i] are the f32 values nearest the decimals listed below (F = 8.6983005 is 0x410B2C3D, e = 0.51 is 0x3F028F5C). With s the file's quant_scale (f32), the channel's base table t_c (raster order) is:


d = max(5 * s, 0.1)            f32 multiply; 0.1 is the f32 0x3DCCCCCD

  b = B_c[i] * F               f32 multiply
  r = dts(d, i)                f32 (below)
  q = r / d                    f32 divide (exactly 1 when d < 1.5)
  t_c[i] = b * q               f32 multiply

and the distance-to-scale dts of raster frequency i is, with D the f32 d and E the f32 e[i] both widened exactly to f64:


dts(d, i) = d                                when D < 1.5
          = f32(max(0.5 * D, P1 * P2))       otherwise, where
            P1 = pow(1.5, 1 - E)             f64 (1 - E an f64 subtract)
            P2 = pow(D, E)                   f64
            0.5 * D and P1 * P2 are f64 multiplies, max an f64 max,
            f32(x) the one rounding to f32

Grouping matters: (b * r) / d is a different f32 program and gives other bits (vectors below). At scale 0.2, t_c is jpegli's table at distance 1.0.

The steps then follow 2.8, in f32: `step_c[i] = max(t_c[i] * s, floor) * mul_c (multiply, max, multiply), with step_c[0]` then multiplied by dc_c / 64 (an exact f32 quotient) and floored at 1/64. The step bound of 2.8 applies; with mul 2 the chroma steps exceed 65536 at s >= 32.78 (quality at or below 1.52), where the reference encoder writes Annex K (matrix 0) instead.

ln, exp and pow are pure f64 arithmetic (no platform libm), each operation rounded as above; ln2 is the f64 0x3FE62E42FEFA39EF and sqrt(2) the f64 0x3FF6A09E667F3BCD. pow(x, y) = exp(y * ln(x)) for x > 0.

  • ln(x), x > 0: normalize x = m * 2^e with m in [1, 2) (its f64

    • exponent and mantissa fields; a subnormal input is first multiplied by 2^54, and 54 * ln2 subtracted from its ln); if m > sqrt(2) then m = m * 0.5, e = e + 1. With t = (m - 1) / (m + 1) and t2 = t * t, evaluate s = 1 / 25; s = s * t2 + 1 / k for k = 23, 21, ..., 3 (1 / k an f64 divide); then ln(x) = e * ln2 + (2 * t) * (s * t2 + 1).

  • exp(x): for x < -700 return 0, for x > 700 return infinity; else

    • with kf = x / ln2, k = trunc(kf + 0.5) when kf >= 0, else trunc(kf - 0.5) (the f64 add rounds first), and r = x - k * ln2; evaluate s = 1; s = 1 + (s * r) / n for n = 20, 19, ..., 1; then exp(x) = s * 2^k (2^k exact: the f64 with exponent field k + 1023).

General seed bank identifiers (Lossy 0.6)

Feature 28 seed_bank_ids gates presence bit 9. The bank ID and scope are separate canonical unsigned LEB128 values. 2.9 Superblocks (feature superblocks)

A lossy payload may code some aligned groups of 8x8 blocks as one larger DCT: 16x16 (2x2 blocks), 16x8 (two blocks side by side: 16 wide, 8 tall) or 8x16 (two stacked blocks). The 8x8 blocks of a merged block are its *parents*. Entropy coding, lanes, contexts and the DC image are unchanged: a merged block's coefficients travel in its parents' 64-slot units and DCs. The reference encoder uses superblocks in the Compact tier (docs/LOSSY.md "Superblocks").

Declaration. Lossy head record 21 (critical, empty payload; a payload is Corrupt) says the payload uses superblocks. It is gated syntax of feature 12 superblocks (0.1): in a file that does not declare the feature it is Corrupt. It combines with entropy 0 (run-level) and 3 (split-Huffman), the only entropy values (1 and 2 are reserved, Unsupported: 2.8). With record 9 (keep blocks), record 27 (channel layouts) or record 23 (small transforms, whose joint map carries merges itself: 2.11) it is Corrupt. With record 5 (exact blocks), 7 (AQ) and 11 (32-bit DC) it combines as below; with record 15 (reconstruction bias, Lossy 0.4) the bias applies to 8x8 blocks only and merged blocks are dequantized without it (2.9.4), and a file may declare both features. Writers write the record only when some unit merges.

2.9.1 Units and groups. A *unit* is the region of one lossy unit record (2.7): R block rows (its stripe's) by C block columns (its column group's; the whole width without groups), with unit-local block coordinates (row, column). Its *groups* are the aligned 2x2 parent squares at even (row, column), in raster order; a group's parents are top-left (TL), top-right (TR, present when column + 1 < C), bottom-left (BL, row + 1 < R) and bottom-right (BR, both). A group whose only parent is TL (the bottom-right corner of a unit with odd R and C) has no symbol and never merges. A merge never crosses a unit, so units stay independent and every stripe, column group and region decodes as before.

2.9.2 The partition map. With record 21, every lossy unit record (id 55) starts with its map, before the selector map of 2.8 record 27 (which a superblock payload never has) and before the entropy-coded data:


map_len      varint    bytes of the map; 0: no group of the unit merges
map          map_len bytes: the range-coded symbols

A non-empty map codes every group's symbol in raster order with an adaptive binary range coder (LZMA's). State: range (u32), code (u32), probabilities (u16, 12 bits) all starting at 2048: any[9] and tree[8][9] (nodes 1..=7 used). The decoder sets range = 0xFFFFFFFF, then code = (code << 8) | next() four times; next() returns the map's next byte, or 0 once the map's bytes are exhausted (it still counts the read). One bit with probability p (a reference to one of the probabilities):


bound = (range >> 12) * p
if code < bound: bit = 0; range = bound; p += (4096 - p) >> 5
else:            bit = 1; code -= bound; range -= bound; p -= p >> 5
while range < 2^24: range <<= 8; code = (code << 8) | next()

(u32 arithmetic; bound never overflows.) The context of a group is `ctx = 3 class(left) + class(up), where left` is the group two columns to the left and up the group two rows up in the same unit, and class is 0 when that group is absent, has no symbol or has symbol 0, 1 for symbol 1, 2 for any other symbol. Per group: merged = bit(any[ctx]); if 0 the symbol is 0; else node = 1, three times node = 2 node + bit(tree[node][ctx]), and the symbol is node - 7 (node 15, tree value 7, is Corrupt). After the last group: a map that merged nothing, or whose bytes were not all read (map_len greater than the number of next() calls, the four initial ones included), is Corrupt; a map of a unit without groups is Corrupt. Writers drop the map's trailing zero bytes, which the decoder reads back as the zeros past its end (the reference encoder ends the coder with the value of the final interval that has the most trailing zero bits, flushes five bytes and drops the leading carry byte and the trailing zeros); zero bytes the decoding reads are valid either way.

2.9.3 Block codes. With a fourth DC channel (records 5 or 7), every parent of a merged block must have the same block multiplier (the AQ multiplier min(max(a, 0), 255) / 64; with exact blocks 1 for code 0), and with exact blocks none may be an exact block (code 1); anything else is Corrupt. A merged block's AC multiplier is its parents' (1 without AQ); DCs are never scaled.

2.9.4 Coefficients. A merged block of W x H pixels (pw = W / 8, ph = H / 8 parents across and down) has coefficients X[v][u], v < H, u < W (row = vertical frequency), filled per color plane c as follows, in f32 (each operation one IEEE single-precision operation, rounded to nearest even, in the order written):

  • *Steps.* T is the plane's 8x8 step table of 2.8 (raster, row = vertical

    • frequency; the DC entry includes the DC multiplier). Along a 16-point axis index k falls on entry k / 2 when even, and between entries `a = (k - 1) / 2 and b = min(a + 1, 7) when odd; along an 8-point axis index k` is entry k. A row value is T[y][x] on an entry and `T[y][a] * 0.5 + T[y][b] * 0.5 between two; the step S[v][u]` is the row value of the vertical entry, or between two vertical entries ra * 0.5 + rb * 0.5 of their row values. (This is bilinear interpolation of T at the coefficient's physical frequency.)

  • *Input scale.* SV[v] and SH[u] are SC16 (a 16-point axis) or SC8

    • (an 8-point axis) below; SC[v][u] = SV[v] * SH[u] and the dequantization factor D[v][u] = S[v][u] * SC[v][u].

  • *LLF.* The parents' DCs come from the DC image (dc[py][px] of parent

    • (py, px): its DC value of 2.8, an i32 clamped to [-2^22, 2^22]): d[py][px] = dc[py][px] * T[0][0]. With `K = 1 / sqrt 2 (0x3F3504F3) and R = 1 / (8 sqrt 2 sin(pi / 32))` (0x3F66DA05), first along a 16-point vertical axis, per column x < pw: `a = (d[0][x] + d[1][x]) * K, b = (d[0][x] - d[1][x]) * K, d[0][x] = a, d[1][x] = b * R; then along a 16-point horizontal axis, per row y < ph: a = (d[y][0] + d[y][1]) * K, b = (d[y][0] - d[y][1]) * K, d[y][0] = a, d[y][1] = b * R. Then X[v][u] = d[v][u] * SC[v][u] for v < ph, u < pw`.

  • *AC.* Parent (py, px) is unit p = py pw + px. Every other coefficient

    • (v, u) is X[v][u] = q * (D[v][u] * m) with m the block's AC multiplier, where the quantized value q (an i32, exact in f32) is unit (v / 8) pw + u / 8's raster slot 8 (v % 8) + u % 8, except that the quadrant origins (8 py, 8 px) of units p > 0 take unit 0's raster slot 8 py + px (unit p's slot 0 holds its DC). Every AC slot of every parent is used exactly once. (m = 1 leaves D as it is.) The reconstruction bias of record 15 does not apply here: a merged block's coefficients are exactly these, while the file's 8x8 blocks reconstruct at (q - sign(q) B) * step as usual.

The reference encoder computes the orthonormal 2D DCT of the merged block and quantizes coefficient (v, u) with step S[v][u] times the multiplier; its LLF coefficients map to the parents' DCs by the inverse of the LLF step, so a block whose parents are flat gives each parent its own mean.

2.11 Small transforms (feature small_transforms)

A lossy payload may code a color plane of an 8x8 block (its *parent*, as in 2.9) as four 4x4 DCTs instead of one 8x8 DCT, chosen per parent and plane. The same partition map carries superblock merges (2.9), so one payload combines both. Entropy coding, lanes, contexts and the DC image are unchanged: a 4x4 plane's coefficients travel in the parent's 64-slot unit and DC.

Declaration. Lossy head record 23 (critical, empty payload; a payload is Corrupt) says the payload uses small transforms. It is gated syntax of feature small_transforms (Compact 0.3): in a file that does not declare the feature it is Corrupt. With record 27 (channel layouts) or record 21 (superblocks) it is Corrupt. It combines with records 5 (exact blocks), 7 (AQ), 9 (keep blocks), 11 (32-bit DC), 15 (reconstruction bias: it applies to 8x8 planes only, 2.11.3) and 17 (color transform), and with entropy 0 (run-level) and 3 (split-Huffman). Writers write the record only when some unit splits a plane (a payload whose units only merge writes record 21).

2.11.1 The joint partition map. With record 23 every lossy unit record (id 55) starts with its map:


map_len      varint    bytes of the map; 0: no group merges and no plane splits

A non-empty map is one stream of 2.9.2's binary range coder (the same state, initialization, bit procedure, renormalization and reading of zero bytes past the map's end): a header of two bits, merges then splits, each coded with probability 2048 that does not adapt (a fresh 2048 for each), then the sections the header announces:

1. Merges (when merges is 1): every group's partition symbol, in raster order of the groups, coded exactly as 2.9.2 codes them (contexts, any[9], tree[8][9]; a symbol whose blocks need an absent parent, and tree value 7, are Corrupt). Merged blocks are gated syntax of feature 12 superblocks: a map of a file that does not declare it in which a symbol is not 0 is Corrupt. Merged blocks follow 2.9.3 to 2.9.5. 2. Split flags (when splits is 1): for every parent of the unit in raster order (unit-local block rows, then columns) that is neither part of a merged block nor *bypassed* (an exact block: record 5 and block code 1; a kept block: record 9 and block code 0), one bit for each color plane c = 0, 1, 2, in that order, that *has AC*: one of the plane's quantized values in slots 1 to 63 of its unit is nonzero (the unit record's coefficients are decoded before its map is read). 1 codes the plane as four 4x4 transforms (2.11.2), 0 as the 8x8 block of 2.8. A plane without AC has no flag and is not split (both codings give it the same pixels, 2.11.4); merged and bypassed parents have no flags and their planes are not split. Each bit has probability split[ctx] (u16, 12 bits, 54 of them, all starting at 2048), ctx = ((3 c + left) 3 + up) 2 + luma: left and up are the split of plane c of the parent to the left and of the parent above in the same unit (1 split, 0 not split, a plane without AC included), or 2 when that parent is outside the unit, merged or bypassed; luma is this parent's split of plane 0 for planes 1 and 2, and 0 for plane 0.

A section the header announces must hold what it names: a merges section whose symbols are all 0, or a split-flags section whose flags are all 0, is Corrupt, and so is a header of two 0 bits; without a section its parents merge nothing (merges) or split no plane (splits). After the last bit: a map whose bytes were not all read (as 2.9.2 counts them) is Corrupt. Writers end the stream as 2.9.2 describes.

2.11.2 Coefficients of a 4x4 plane. The plane's pixels form four tiles, tile (ty, tx) (ty, tx in {0, 1}) covering rows 4 ty..4 ty + 4 and columns 4 tx..4 tx + 4 of the parent. Tile (ty, tx)'s orthonormal 4x4 DCT coefficient (fv, fu) (row = vertical frequency) is in raster slot `(2 fv + ty, 2 fu + tx) of the plane's unit, 8 (2 fv + ty) + 2 fu + tx`, except for fv = fu = 0: the four tile DCs take a 2x2 orthonormal Haar transform, whose LL is the parent's DC (slot 0, the DC image's value of 2.8, clamped as there), and whose details sit in slots 1 (horizontal: left tiles minus right), 8 (vertical: top minus bottom) and 9 (diagonal). Every slot of the unit is used. For the same pixels the LL equals the 8x8 block's DC, so the DC image is the same whatever the planes' split.

2.12 Native quantized component bands (feature native_components)

Historical v2 experiment; forbidden in v3. Every v3 reader rejects feature 18, including an over-declaration on ordinary data or an outer document. The version-3 assignments 29, 61 and 80 remain reserved and must never be reused. An encoded-domain converter rejects native-component input instead of upgrading it. The optional native-jpeg implementation retains v2 reading and experimental v2 writing; normal and browser builds omit it. The description below preserves the experiment for research and is not an alternative v3 grammar.

In v2, feature 18 permits this DATA grammar instead of section 2.8. The primary header has coding 2, U8 Gray or RGB, and stored dimensions. It does not reinterpret native components as YCoCg: record 29 defines their meaning. This grammar is independent of feature 17 / record 23 and record 27.

This local discriminator selects native syntax; over-declaring feature18 on an ordinary payload or outer document does not select native syntax. Native syntax without feature18 is Corrupt. 2.13 Quick-pixel units

Feature 22 quick_pixels selects a lossless coding alternative through head presence bit 3. It preserves every stored sample bit, including unused significant bits, signed representations, floating-point NaNs and negative zero. Channel and color meaning remain in the normal header; this mode performs no color conversion. Older decoders reject the feature at header admission.

With bit 3 set, lanes MUST be 1. The channel maps, models_len and models are absent. The optional head-record list follows group_cols directly. Palette, seed-bank, near-lossless and bilevel syntax MUST NOT accompany quick coding. Unit hints, reservations, indexes, checksums and unit ordering are unchanged. Each main stripe record (id 59) contains a one-byte mode followed by its body:

  • 0, raw: exactly unit_width * unit_height * channels * sample_bytes

    • bytes, row-major interleaved, each sample little-endian.

  • 1, packets: the packet stream below, with exactly that many pixels and

    • no trailing bytes. No inner signature, dimensions or end marker occurs.

  • 2, bit-smart planes: the exact byte-plane body in 2.13.1. It requires

    • lossless head bit 4 and feature 23.

  • Other modes are Unsupported; missing mode/body bytes are Corrupt.

Each unit starts independently. Let D be the sample storage width (8, 16, 32 or 64). All arithmetic is unsigned modulo 2^D, even for signed or float sample types. Maintain tuple (r,g,b,a), initially (0,0,0,2^D-1), and a 64-entry tuple cache initially all zero. One/two-channel storage represents (x,x,x,a); three/four-channel storage represents (x,y,z,a). A missing fourth component is internal state only. For CMYK the fourth component is K; this tuple convention never changes its channel identity or interpretation.

Read the next byte, testing literal values before the top-two-bit families:

TagOperation
FERead one color word for 1/2-channel images or three for 3/4-channel images; preserve a.
FFAs FE, followed by one word for a.
00xxxxxxReplace the tuple with cache entry xxxxxx.
01rrggbbAdd each two-bit field minus 2 to r,g,b; preserve a.
10gggggg then rrrrbbbbLet dg=gggggg-32; add dg+rrrr-8, dg, dg+bbbb-8 to r,g,b; preserve a.
11xxxxxx (except FE/FF)Output the previous tuple xxxxxx+1 times (1–62).

Literal words are little-endian and D/8 bytes each. For 1/2-channel storage, color literals set all three color tuple components to the same word. After every output pixel, insert its complete tuple into the cache. Its index is (3*fold(r)+5*fold(g)+7*fold(b)+11*fold(a)) mod 64, where fold sums all bytes of a word. For 1/2-channel images the three color components MUST be equal at every output pixel; otherwise the stream is Corrupt. Emit the storage's 1–4 components without interpreting their bits. Runs may cross rows within a unit but MUST NOT exceed its pixel count. A decoder validates the stream's end when the last unit row is decoded; region requests need not decode unrequested later rows.

The initial zero tuples occupy every cache slot even though their hash is zero. An INDEX selecting an untouched initial slot still inserts its tuple at the computed hash above; slot zero may previously have held another tuple.

An encoder may choose raw whenever packets would be larger. This choice needs no separate feature or entropy model and cannot change reconstructed pixels. Quick units have no reference predictor; an animation may still inherit pixels outside a changed rectangle or reuse an empty frame through the common renderer.

Decoder scheduling does not alter this grammar. Independent units may be reconstructed in any order into their corresponding output rectangles; tuple and cache state MUST NOT cross unit boundaries. An implementation may reconstruct several streams together or use fewer workers than requested, provided it preserves the per-unit packet state, output bits and extent checks above.

The packet families follow Dominic Szablewski's QOI v1.0 specification. The generalized sample widths and IMI framing above are IMI syntax, not QOI files. The implementation is original; provenance and interoperability evidence are linked from the quick-pixel study.

2.13.1 Exact bit-smart quick units

Feature 23 quick_bit_smarts and lossless head bit 4 allow unit mode 2; head bit 4 without bit 3 or without feature 23 is Corrupt. A mode-2 unit without head bit 4 is Corrupt. Maps/models remain absent. Encoding is opt-in; ordinary quick encoding keeps its existing wire bytes. Over-declaring the feature is allowed, and raw/ordinary packet units may coexist with mode 2.

There are exactly N = channels * sample_bytes byte planes, in stored component order, least-significant byte first within each sample. Each plane reconstructs unit_width * unit_height bytes in row order. No per-plane dimensions, sample meaning or cross-unit state are introduced.

The cheap encoder policy considers raw/constant/dense-mask/dictionary bodies and duplicate-plane reuse. An encoder may choose any exact valid representation, including an ordinary raw/packet unit when smaller. Policy/selection heuristics are not wire semantics. The renderer and metadata remain common to every mode.

The decoder retains at most N plane states plus one interleaved row's byte scratch for each live unit. 2.14 Template palette stripes (feature template_palettes)

A payload may code a palette stripe (2.5) of up to 256 entries with a template model instead of predictors and tokens. Per pixel, one binary symbol says whether the pixel's index differs from its left neighbor's, in a context of which nearby pixels equal that neighbor. A pixel that differs then tries up to five neighboring indices in turn, and an index none of them matches is coded directly. A row equal to the row above codes nothing (a *typical row*). Lossless head record 35 holds the probabilities, the direct-index table and optionally entries shared by the payload's stripes. The record is gated syntax of feature template_palettes and is corrupt in the nested images of a lossy payload and in a payload of quick-pixel units (2.13). Stripe layouts 0x83 and 0x84 use it and are corrupt without record 35; they do not need head present bit 0.

The stripe decodes an index i(r, c) per pixel. Lanes and steps are those of 2.3, and the ten template pixels t_k = i(r + dy_k, c + dx_k) are those of 2.10 with the same rules: 0 for rows above the stripe and columns outside the group, and a pixel of the current row left of the lane's first column reads the pixel one row up at the same column. W = t_9 is the left neighbor. A typical row (its bit set) copies the row above, decodes no symbol and leaves every state unchanged; the template of later rows reads the copied values. Every other row decodes, per step, these phases, each over the lanes taking part in ascending lane order, so words are consumed in order (step, phase, lane):

1. Phase 0, every active lane: with ctx = (W == 0) << 9 | sum over k = 0..=8 of (t_k == W) << k, p = p_ctx and slot = x_l mod M, decode m = 1 if slot >= p, else 0 and update the state as in 2.10 (with t = m), then renormalize (3.1). m = 0: i = W. m = 1 with n <= 2: i = 1 - W (W is 0 or 1). m = 1 with n >= 3: the lane is *open*. 2. Candidate phases j = 0..=4: candidate c_j is `t_5, t_6, t_4, t_8, t_1 (N, NE, NW, WW, NN). An open lane takes part when c_j` differs from W and from c_0 .. c_(j-1). With q = q_(8 j + min(count of k = 0..=9 with t_k == c_j, 7)), decode b = 1 if slot >= q, else 0 and update the state the same way; b = 0: i = c_j, and the lane is no longer open. 3. Escape phase, every lane still open: decode a symbol s with the direct-index table as a token (3.1: slot lookup, state update, renormalize) and set i = s. Without the table the escape decodes 0 and leaves the state unchanged (all of M on symbol 0).

Each index i selects entry i of the stripe (entry 0 when i >= n), and its slot values go through the channel maps (section 4, step 4) as in 2.5. A unit of an inter frame decoded this way does not read the reference.

With two entries the phase 0 context is a bijection of the bilevel context (2.10) on the values themselves, so a decoder may slide that context from step to step and look the probability up one step ahead, as for bilevel stripes.

2.17 Consecutive DC coverage (feature dc_coverage)

Head record 45 is critical. Its payload is:


version         uvarint = 1
column_lists    uvarint; 1 (shared boundaries) or the image's column-group count
for each list:
  span_count    uvarint
  coverage      span_count positive uvarints

Each value counts consecutive AC stripe rows, not individual column units or pixel rows. Each list sums exactly to the image's AC stripe count. The first span starts at AC stripe 0; every next start is the preceding end. Zero counts, under/overcoverage, arithmetic overflow and trailing bytes are Corrupt. The number of spans is bounded by the AC stripe count before storage is admitted. A single list applies to every column group; otherwise each group uses its own list. Starts and ownership are derived by prefix sums; no owner ID is repeated in every AC unit.

At AC unit (stripe,group), write a DC main record first exactly when that stripe begins one of that group's spans, followed by ordinary alpha, AC and exact records. Record ordinals, unit-table entries, reservations and trailing indexes count this derived order. The root numeric head's stripe height is an admitted maximum: it must be a multiple of the AC stripe's block-row height and at least the tallest covered DC rectangle. It does not override the rectangles' derived starts or ends.

3. Entropy coding: interleaved rANS

16-Lane Interleaved rANS

16 independent rANS state machines are interleaved so a single AVX-512 register (or two AVX2 / four NEON registers) decodes all 16 lanes in lockstep. Each lane refills from the bitstream independently — no serial bit-level dependencies.

Per stripe and slot there is one stream:


initial states   u32 per active lane, each >= 2^16

Each active lane l holds a state x_l in [2^16, 2^32). Tables have M = 2^10 slots. Inactive lanes and positions past a lane's width decode nothing.

3.1 Decoding one step

For every step, first the *token phase* runs over lanes in ascending order, then the *extra-bits phase* runs over lanes in ascending order. Whenever a state drops below 2^16, it is renormalized with the next word of the stream: x = (x << 16) | word. Words are therefore consumed in order (step, phase, lane). At most one word is read per lane per phase.

A lane that is inside a zero run skips the step (decrement its run counter, output 0) and takes part in neither phase.

Token phase for lane l at lane column x, stripe row r:


T(v) = min(v >> ctx_shift, 2^16)        # baseline: T(v) = v
uw = (x > 0) ? T(u[r][x-1]) : 0       # this slot, this lane
un = (r > 0) ? T(u[r-1][x]) : 0
sum = (x>0 && r>0) ? uw + un
    : (x>0)        ? 2*uw
    : (r>0)        ? 2*un
    :                0
if cross: sum += T(u0[r][x])           # slot 0 residual, same position
class = min(bit_length(sum), 15)
ctx   = ctx_map[class]                 # 0..=3
slot  = x_l mod M
(sym, freq, cum) from the table of ctx: cum[sym] <= slot < cum[sym] + freq
x_l   = freq * (x_l >> 10) + slot - cum[sym]
renormalize

Extra-bits phase: n1 = min(nb, 16) extra bits of the token (3.2) are taken from the state: e = x_l mod 2^n1; x_l >>= n1; renormalize.

High extra-bits phase (extended tier only; empty when nb <= 16): n2 = nb - 16; e |= (x_l mod 2^n2) << 16; x_l >>= n2; renormalize.

Words are consumed in order (step, phase, lane) over the token, extra and high-extra phases.

u values are zigzag residuals (section 5). A value token yields u = base + e. A run token yields len - 1 = base + e: the current position and the next len - 1 positions *of this lane* (in lane order, skipping positions past the lane width, continuing across rows) are 0.

3.2 Tokens (hybrid integers)

A model has parameters k and m. For slot depth n:


kv = min(max(k, m), n)          # value scheme
value tokens:  2^n if kv >= n, else 2^kv + (n - kv) * 2^m
rk = max(kv, m), rm = m         # run scheme
run tokens:    2^rk + (24 - rk) * 2^m     (follow the value tokens)

Token t of a scheme with parameters (k', m) decodes as: if t < 2^k', base = t, nb = 0; otherwise q = t - 2^k', msb = k' + q / 2^m, nb = msb - m, base = (2^m | (q mod 2^m)) << nb.

The alphabet (value + run tokens) is at most 256 symbols. A single run token never exceeds 2^15 positions.

3.3 Models

The models bit stream (section 2) holds one model per slot in slot order, then, when the head's present bit 0 is set, the palette index model (slot depth n = 8). Each model:


k            5 bits   0..=16
m            3 bits   0..=4
cross        1 bit    written in every model; may be 1 only in slots 1 and
                      2 of an RGB or RGBA image (for 64-bit samples the hi
                      words' slots 1 and 2, 2.2), else 0
ctx_shift    5 bits   present only when the slot depth n is over 16
                      (absent and 0 otherwise); any value 0..=31
ctx_map      16 x 2 bits, class 0 first
tables       one per context 0..=max(ctx_map), in context order; a context
             above max(ctx_map) has no table and is never selected

In a table blob that carries seed selectors (lossy files' nested DC and alpha images, "Seed tables" below) each table starts with its selector bit.

Table: quantized symbol weights, normalized to M:


last         8 bits     highest symbol with nonzero weight
prec - 1     3 bits     mantissa precision 1..=8
for sym in 0..=last:
  e: exponent (bit length of weight; 0 = absent), coded as
     gamma(zigzag(e - e_prev) + 1), e_prev starting at 0
  if e > 1: min(e-1, prec-1) mantissa bits below the leading one
weight = 0 if e == 0; 1 if e == 1; else ((1 << nb) | mant) << (e - 1 - nb)

gamma(v): z zero bits, a one bit, then the low z bits of v, where z = floor(log2 v).

Normalization (deterministic integer arithmetic, 64-bit): W = sum(weight); f = max(1, floor(weight * M / W)) for each nonzero weight; order nonzero symbols by weight descending, then index ascending; while sum(f) < M add 1 to the next symbol in that order (cycling, from the first); while sum(f) > M subtract 1 from the next symbol in that order whose f > 1 (cycling, from the first). cum is the prefix sum.

Validity. A decoder checks each model as it reads it, before anything decodes; each of these is Corrupt:

  • k > 16 or m > 4;
  • k other than the scheme's kv = min(max(k, m), n) (3.2): writers write

    • the clamped value, so k < m (unless k = n) and k > n are corrupt (n = 8, k = 0, m = 1 is, though its kv would be 1);

  • a scheme whose alphabet (3.2) exceeds 256 symbols;
  • cross = 1 outside the slots named above, or in the palette index model;
  • in a table: last at or past the alphabet; a gamma code with more than

    • 24 leading zero bits; an exponent e outside 0..=32; no nonzero weight; weight on a run token past the run cap (3.2);

  • a seed selector that names no seed (see "Seed tables");
  • a bit stream that needs more bits than models_len bytes hold.

Padding. After the last model the stream may end anywhere inside models_len bytes. Decoders do not read or check the rest: the bits after the last table and any further bytes are ignored. Writers pad the last byte with zero bits and write no further byte, so models_len is the number of bytes the models' bits fill (ceil(bits / 8)).

5. Encoder notes (non-normative)

The reference encoder picks, per stripe, the decorrelation mode and per row the predictor minimizing a bit-length proxy; groups the 16 context classes into up to 4 contexts by greedy merging; codes zero runs of at least 4 positions as run tokens; and chooses the table precision minimizing table plus data bits.

Palette stripes: the encoder collects a stripe's slot tuples (up to 256), orders the entries by the sum of their slot values, codes the index plane with the same predictor search, and keeps the palette stripe when a bit-length entropy estimate of the index residuals plus the entries is below that of the slot residuals.

Bilevel stripes (2.10): for a payload with one 1-bit slot, or (bilevel palette stripes, the same two entries in every unit, the commoner first) an image of exactly two slot tuples that allows palette stripes, the encoder takes inv so that the majority value reads as 0 (like the area outside the image), counts each context's zeros and ones over every unit, and writes p_c = round(M * zeros / (zeros + ones)) limited to 1..=M-1 when both occur (M or 0 when only one does). It codes every unit both ways and keeps the bilevel stripe where it is smaller, writing record 25 only when the units' saving exceeds the record's bytes (jointly with template palette stripes when those are tried, below); nested images of lossy payloads never use it.

Template palette stripes (2.14): in a payload that allows palette stripes and has no near-lossless bounds, with every slot at most 16 bits deep, the encoder orders entries by count, most frequent first (so index 0 is the commonest, like the area outside the stripe). When the whole image has at most 256 slot tuples, they are the shared entries, and each unit uses them (0x84) unless it has at most two tuples of a larger shared set, which it codes with its own (0x83, the two-entry rule of phase 0); otherwise each unit with at most 256 tuples has its own. The encoder marks the rows equal to the row above, counts each context's outcomes over the other rows of every such unit, picks the probability precision with the smallest record plus estimated stream size, and writes the direct-index table with the smallest total size (3.3). It codes those units both ways and writes the tables (none, bilevel, template, or both) giving the fewest bytes, each unit taking its smallest allowed coding and each record counted with its framing; ties keep fewer tables. Nested images of lossy payloads never use template palette stripes.

Column groups: by default images at least 8192 pixels wide use G = 2048 (lanes of 128 columns, like a 2048-wide image); narrower images use none.

Near-lossless (2.6): the encoder runs the decoder's reconstruction while it encodes. Per row it tries each allowed predictor on the reconstructed rows above, reconstructing the row left to right per lane, and keeps the one with the lowest bit-length proxy under the best decorrelation mode; the stripe's mode minimizes the total over the chosen rows. From a bound B in sample units it derives each channel's coded δ: B for Lsb and Offset maps, B >> (D - n) for Shift, an exhaustive search over the coded range for Replicate and Scale, capped at 2^(n-1) - 1. When an unsigned channel declares fewer significant bits than its storage and its map could expand a clamped value above the declared range, it uses an Lsb map instead; an Offset base is lowered so that value + 2^n - 1 does not pass 2^32. A channel whose coded δ is 0 stays exact, and a payload with no nonzero δ, or whose units are all palette stripes (exact), is written without record 19 (and its file does not declare near_lossless).

FloatShift (map 8): the encoder ORs the raw float patterns of a channel and uses map 8 when it codes fewer bits than the map otherwise chosen, or as many as an F16InF32 map (whose f16 mantissa then holds dead low bits). Data whose low bits are zero and whose samples are all positive is already coded at its precision by Shift, so it keeps Shift and needs no float_shift feature. The reference encoder does this by default (EncodeConfig::float_shift, on by decision of 2026-10-09); with it off, it never writes map 8.

Value tables (map 9): for a file's own payload, the encoder considers every exact coded channel (not Const, no near-lossless bound) of words wider than 8 bits whose distinct values leave gaps in its regular map's coded range, up to 2^14 entries (8-bit words keep their maps: palette stripes cover them, docs/VALUE_TABLES.md). It estimates each choice with the predictor search and token-entropy estimate on up to 16 windows of up to 256x16 pixels scaled to the image, plus each table's exact bytes: all candidate tables, then one greedy pass toggling each channel. It keeps the regular maps unless the estimate is 1% smaller. Nested lossy images never use tables.

Seed tables (2026-10-07)

A lossy file may replace run-level or split-Huffman AC tables, and slot tables of its nested DC/alpha images, with immutable built-in seed tables. In each seeded blob every table starts with one bit: 0 explicit, 1 followed by a ceil(log2 n)-bit seed index. Seed and explicit forms with identical weights have identical decoding semantics.

New files select the bank and AC/DC/alpha scope with presence bit 9 and feature seed_bank_ids (Lossy 0.6), as specified in 2.8. This is an open u64 varint namespace with one capability; unknown banks are Unsupported. Legacy bit 0 and seed_bank_1 retain their packed-byte grammar and bank-1 validation. Nested files have their own declarations. Bank 1 remains the unchanged asset imij/src/seeds/bank1.bin; layout, kinds and frozen identity. New bank IDs never change the meaning of old ones. The default encoder prices the complete file and retains the unseeded candidate when smaller. Standalone lossless use remains lab-only rather than a normative profile feature.

Exact blocks in lossy files (2026-10-07)

A lossy payload may code some 8x8 blocks losslessly: lossy head record 5, for 8-bit RGB and RGBA only, gated by feature exact_blocks (Compact 0.1), so a decoder without it fails with Unsupported from the header. Record 5 in a file that does not declare the feature is Corrupt; a file may declare it without exact blocks. Previews, frames, gain maps and plane tiles are files with their own headers, so the rule applies to each. The DC image's fourth channel marks them (block code 1; 0 = lossy), their AC are coded as end-of-block, and their source pixels come from a nested lossless RGB image that lists the exact blocks in decode order, packed into rows of up to 64 blocks. A nested stripe sits in the exact record (id 57, after the AC record) of the unit holding its first block; the exact head gives every unit's exact block count and every nested stripe's size, so a reader locates the stripes any unit needs from the head alone (region readers decode exact blocks from the head, their units' records and those stripes). The normative layout, decoding and validity rules are in docs/LOSSY.md ("Format as built", "Exact blocks").

Named planes and compressed metadata (2026-10-04)

Planes and ROI specifies the pDAT, pIDX and sLOC extension, independently typed tiled levels, packed-color sharing, attachment references and seek validation. Explicit source precision (2026-10-04)

The sig_bits header field (section 1.0, present bit 7) declares each source component's significant integer bits, one byte per channel, each in 1..=storage_bits; floating components must declare all storage bits. Zero or oversized widths are corrupt. Full-storage encodes omit the field in the masked form.

Lossy unsigned samples use the declared right-aligned code range, independently per source component. They are normalized before color conversion and rounded directly back to the declared grid. Lossless coding still preserves all stored bits. Source declarations do not reduce color-transform or coefficient widths. Unit index for streaming writers (2026-10-11)

This is an outer format. It allocates no IMIJ feature bit or image record ID. Every current entry is an independent, byte-identical blob. Absolute offsets are u64; integers below are little-endian unless called unsigned LEB128. There is no leading header or per-blob framing. Index pages may occur between blobs. Never concatenate or decode index bytes as part of an image.

The archive is one logical byte stream. Its footer and page/blob offsets do not describe physical transport splitting; neither a part size nor a part count is stored in the archive. A separate transport manifest must map logical ranges to physical objects. Repartitioning identical archive bytes leaves the archive grammar, offsets and digests unchanged. Part count and total logical length may be published after a forward writer commits its footer. Loose part files alone do not provide the mapping required by a random-access reader.

Each append segment has an algorithm for its blobs, index pages, and footer. The footer names its IMIJ digest algorithm ID (IMIJ SPEC 1.4.2). IDs 0 and 1 are XXH3-64 and XXH3-128, with XXH3-128 as the writer default. The optional BLAKE3 and SHA-2 implementations enable IDs 2–6. A reader refuses algorithms its build does not support.

Index branches and leaves store the algorithm's complete digest. A 32-byte fixed checksum slot stores the first min(width, 32) bytes in wire order. Unused bytes are zero and readers enforce that padding. A slot containing a prefix verifies those bytes of the declared algorithm's digest. This rule preserves existing files. Older readers reject segments using the newly admitted algorithms wider than 32 bytes.

A split can be packaged as a governed scope. The outer archive indexes the scope as a blob. The scope has its own directory for images, scores, and other associated data.

Index pages

Every page starts with kind u8 (0 basic leaf, 1 legacy branch, 2 metadata leaf, 3 dictionary leaf, 4 dimension-bounded branch, 5 dimension/CICP-bounded branch, 6 dimension/CICP/filename-bounded branch, 7 governed metadata leaf), level u8, count u16. Pages are at most 65,536 bytes. A parent records the full page digest. Branch pages have 1..128 children, leaf pages 0..256 entries (an empty leaf is the empty segment root). Children have strictly increasing maximum keys. All child page ranges end before their parent.

A branch child is three u64 values, maximum key, page offset, page length, then the page digest at the algorithm's width. Its level is the parent level minus one. Writers build pages bottom-up with at most 127 pending child descriptors per level. No all-entry directory or all-page-offset vector is required.

Kind 4 appends four u32 values to each child descriptor (24 bytes plus the digest): minimum and maximum declared width, then minimum and maximum declared height. Bounds include zero for opaque/unknown entries and cover every descendant entry. Kind 5 adds two more u32 values to each child descriptor: minimum and maximum declared CICP key. Key zero means absent CICP; a present value is one plus the little-endian u32 formed from primaries, transfer, matrix and full-range 0/1 bytes. This key is an index ordering, not a new color code or image authority. Kind 6 adds two big-endian u128 values to each child descriptor: minimum and maximum filename keys. A key is the first 16 bytes of the UTF-8 filename, zero-padded on the right; absent filename has key zero. Valid filenames contain no NUL, so the absent key cannot collide with one. Different filenames may share a prefix key; leaves always compare the complete filename. Kind 6 descriptors are 80 bytes plus the digest (96 with XXH3-128). New writers emit kind 6 branch pages, including when all entries omit CICP or filenames; kinds 1, 4 and 5 remain readable. The footer and leaf grammar are unchanged. A fetched child checks advertised bounds against its actual leaf entries or descendants with matching declarations. A query may skip a disjoint child without fetching it, so skipped pages are not fully verified by that query. A complete listing still visits and validates every index page.

A basic leaf begins with six unsigned LEB128 column lengths, followed by the six columns. Each column has exactly count values, with no trailing bytes:

1. key deltas, unsigned LEB128 (first relative to zero); 2. absolute blob-offset deltas, unsigned LEB128 (first relative to zero); 3. blob lengths, unsigned LEB128; 4. image prefix/head sizes, unsigned LEB128 (zero unknown); 5. blob digests, each at the algorithm's width; 6. summaries: width and height unsigned LEB128 (u32), channels/sample/coding each u8, known feature-mask low 64 bits unsigned LEB128.

A metadata leaf (kind 2, level 0) instead has eight column lengths. The first six columns retain exactly the basic layout, followed by:

7. Per-entry CICP presence byte (0/1), four code-point bytes when present (primaries, transfer, matrix, full-range 0/1), then image count unsigned LEB128 (zero unknown, otherwise positive). 8. Per-entry unsigned LEB128 metadata byte length followed by those bytes. Zero length means no filename or attributes. Nonzero lengths are at most 16,384. Each payload is: filename presence 0/1; if present, byte length unsigned LEB128 plus UTF-8; attribute count unsigned LEB128 (0..64); then attributes in strictly increasing UTF-8 key-byte order. Each has a length-prefixed UTF-8 key followed by a type byte and value.

Value types: 0 UTF-8 text and 1 arbitrary bytes (both length-prefixed unsigned LEB128); 2 unsigned u64, 3 two's-complement i64 and 4 finite IEEE binary64 (all eight little-endian bytes); 5 boolean (one byte, exactly 0 or 1). Unknown types reject this leaf. Names contain no NUL: filenames are 1..4096 UTF-8 bytes, keys 1..128. Duplicate/out-of-order keys, invalid UTF-8, nonfinite floats, trailing payload bytes and over-limit lengths are errors. Filename syntax is otherwise opaque; it does not authorize any filesystem operation.

Writers use basic leaves if all new fields are absent; metadata leaves can hold entries with absent fields. Page-size limits may close a leaf before 256 entries. Basic and metadata leaves may coexist within a segment and across appends; old experimental readers reject kind 2 rather than misinterpret it. All indexed metadata is covered by the page digest. Compaction preserves it.

Keys increase strictly; blobs in a segment are nonoverlapping and in write order. Each blob ends before its leaf. A zero-length blob is allowed. A prefix hint cannot exceed its blob. Summaries are caller-supplied cached descriptions, not permission to bypass an image's header or feature admission. Zero dimensions represent opaque/unknown content. Future feature bits not expressible in the summary must be read from the standalone image; this cache is not authoritative.

LEB128 must be shortest-form, at most ten bytes, and fit u64. Checked arithmetic precedes range conversion/allocation. The page-size, level and count bounds apply before entry allocation. Full scans verify the segment entry count, key order and cross-leaf blob order/nonoverlap. Each fetched child page must match its advertised maximum; point lookup verifies the pages it traverses.

Appending and scale

An append batch has a new sorted index and footer linked to the prior commit. Newer entries replace older entries with the same numeric key. Listing merges sorted segment cursors and filters only after resolving replacements. No rewritten directory proportional to the archive size is required for append. Lookup cost grows with segment count; compaction creates one new sorted segment. The format does not require a footer after every tiny blob: batch commits amortize footer and index overhead.

Dimension queries walk kind 4/5/6 bounds and scan legacy kind 1 branches. Exact CICP queries walk kind 5/6 bounds and scan older kind 1/4 branches. Exact filename queries walk kind 6 prefix bounds and scan older kind 1/4/5 branches; every candidate checks its full UTF-8 filename. A query for absent CICP uses key zero. Results are newest-segment first and ascending by key within each segment, not globally key-sorted. For older candidate entries, point lookup checks the latest generation before returning them; a newer nonmatching replacement hides an old match. Bounds filter cached declarations only. An image header remains the authority for dimensions and other semantics.

Independent leaf requests may be batched. Root and footer usually fit in the same tail request.

Page placement is the writer's choice; the grammar above holds either way. The default writer emits each page as soon as it fills, between blobs. A writer may instead emit a segment's pages after its last blob, in level order: every leaf in key order, then each branch level in key order, the root last, then the footer. The branch levels then sit together just before the footer (one tail read), and the leaves of a key range form one contiguous byte range. An IMIJ entry is fetched through an entry-relative bounded ReadAt adapter; its own DATA locator/unit index governs region requests. Archive head-size hints do not alter IMIJ offsets, framing, checksums or interpretation.

Object-store segments can each use this format without append support. A future manifest API must publish immutable object identities through conditional replace; it must not emulate append by rewriting a multi-gigabyte object for each entry.

Shared entropy/image seeds are a separate opt-in dependency design, not an implicit interpretation of these entries. See ARCHIVE_SEEDS.

Per-leaf string dictionaries

Kind 3 is a metadata leaf with nine columns. Columns 1–7 are unchanged. Column 8 has the same per-entry length prefixes and typed metadata grammar, except each filename, attribute key and text value replaces its string length with an unsigned LEB128 token: even 2*n means n following literal UTF-8 bytes; odd 2*i+1 references dictionary index i. Byte values remain length-prefixed raw bytes. Empty metadata remains a zero-length payload.

The count is positive, strings are nonempty and at most 16 KiB, and references must be in range. No recursive or cross-page references exist. The dictionary borrows from the bounded page. Expanded metadata is validated by the same shared item-metadata parser, retaining all name, value, ordering and per-entry limits. Writers retain the previous uncompressed leaf budget and choose kind 3 only when the entire serialized page is smaller. Repeated strings are candidates; unique strings stay literal. This adds no image-format record ID, feature bit or blob dependency.

Optional sequence seek blob

An image entry may carry the typed bytes attribute imij.sequence-index. It contains a version (u8), index-entry key and index-blob length (two u64), the digest algorithm ID (u8), and the complete index-blob digest. Version 2 stores digests up to 32 bytes in the padded slot and is 50 bytes total. Version 3 stores wider digests at their exact width, for a total of 18 + width bytes. Version 1 is read for migration only. The index is an ordinary blob; it uses no special archive page, IMIJ record or feature bit. Entries without it keep their existing bytes. Replacing the index key with different length/digest makes the old reference fail. Compaction copies both entries and the reference unchanged.

The blob has a 96-byte header: IMIJSEQ followed by version byte 3, 4, or 5, image-file length (u64), the index digest algorithm id and the image digest algorithm id (one byte each), reference digest suffix capacity (one byte), five zero bytes, the image-file digest in a 32-byte slot, positive image count (u64), then the header digest slot: the index algorithm's digest of the preceding 64 bytes. Versions 3 and 4 use zero suffix capacity. Version 5 uses 32 or 96 bytes per record, enough for a 64- or 128-byte reference digest. Length is exactly 96 + (96 + suffix_capacity) * count, with checked arithmetic. The encoded image length and digest slot are checked against the expected length and complete digest of the image entry. (Version 1 and 2 blobs, with 48- and 96-byte records, are rejected and rebuilt; 2026-10-25.)

1. Absolute offset of the fRAM tag relative to the outer IMIJ file, or u64::MAX for an empty legacy update (u64). Version 3 stores the nested image offset here. 2. Explicit reference-raster digest in a 32-byte slot, zero when absent (the digest of IMI frame record 111 (33 under IMI header version 2), under its own algorithm). 5. The primary record covers the entire image file, has prefix length zero and is independent. Empty legacy updates also have prefix length zero. A nonempty version 4 nested record has a positive prefix length. The nested offset is computed with checked addition. Other nonempty ranges must lie within that file. Empty records require an earlier reference and zero length. Reference hashes require a reference; every reference ordinal is strictly smaller than the item's ordinal. These conditions reject cycles but do not bound traversal length; applications set their own cache and work budgets. Hashes detect accidental corruption, not authenticity.

Opening reads the header, and a positional lookup reads one record. Archive lookup additionally checks its ordinary index pages. Partial reads do not verify the full blob digest; Reader::copy_to does. Cached coordinates do not replace outer IMIJ admission, item metadata, reference/canvas checks or the native renderer. The ordinary frame decoder takes a complete file. The imij-set selective decoder uses the index to fetch only the primary records and nested files on one dependency chain, checking each selected fRAM control, nested checksum and reference-raster hash. Its caller must bind the source to an immutable object identity. It requires aNIM kind 4 and rejects legacy animations, empty legacy updates and later items with supported outer pixel or file checksums, whose validation needs complete-file admission. This is selective span fetching, not a general incremental compressed-input parser.

It checks covering cSUM pieces and compares the complete reconstructed raster to its pSUM when supported, including every decoded reference. It fails when the caller disables checksum verification or a declared cSUM cannot be verified. These checks cover the selected spans and rasters. Full archive blob digest verification remains a separate operation. The selected nested file immediately follows its own fRAM controls. Their prefix is capped at 64 KiB by the selective reader. In version 4 the absolute offset skips ancillary chunks between items. A version 3 index uses the previous nested extent's end or the primary end and consequently needs adjacent items. The prefix length ends before the nested file. The reader can inspect its pre-DATA metadata separately, without fetching its whole head.

Container upgrade contract

upgrade_container rewrites committed generations oldest first using the current page/footer encodings. It retains the generation chain and each segment's algorithm, so blob digest identities and typed sequence-index references are stable. All referenced blobs are read and verified, including older replacements. Unreferenced gaps and torn tails are not copied; a torn source must first be opened explicitly with Reader::recover.

This operation treats blobs as opaque. Their IMI, nested archive and sequence index versions do not change. A container rewrite is not an image-format or sequence-index migration and does not make a previously unsupported blob readable. It also cannot update application-owned external offsets; callers must rebuild those from the new archive. The returned snapshot refers to the new output only. Source/sink aliasing is forbidden. A write or verification error leaves incomplete output; do not publish it even if an earlier rewritten generation can be opened. No filesystem rename or durability policy is implied.

Validation: just test-imij-set covers v1/v2 and mixed XXH3-64/128 append chains, historical snapshots and metadata, sequence-index bindings, empty legacy generations, digest and sink failures, and a 64 MiB virtual blob with 64 KiB input/output request caps. The virtual-blob test checks streaming I/O and exact bytes; it does not measure process RSS.

Compaction differs: it keeps only the latest entry for each key in one segment. It preflights index metadata, preserving a common source digest algorithm or selecting the algorithm required by retained sequence bindings. With no such bindings, mixed sources use the default algorithm. Conflicting requirements cannot fit one segment without rewriting opaque index blobs and are refused before output. upgrade_container preserves separate algorithms instead.

Image and archive upgrade contract

upgrade retains the container history described above and additionally uses imij::upgrade_image on each IMI entry. Recognition uses the complete eight-byte IMI signature, or the eight-byte archive footer marker for the version at its matching footer position. Malformed recognized entries fail. Other ordinary blobs, including image attachments and unknown ancillary data, remain byte-identical. The batch migration and compaction APIs refuse governed scopes. Scope publishers can build a new revision with an updated policy through the governed writer.

IMI migration rewrites V2/V3 framing to V4 recursively: DATA record ids, legacy checksum declarations, frame reference digest tags, frames/pages, previews, gain maps and plane tiles. It preserves entropy payloads and raster digests, recomputes encoded-byte checksums, and relocates DATA/plane indexes. Unsupported critical syntax or checksums that cannot be recomputed fail. This verifies framing and file checksums, not entropy decoding or pixel-checksum correctness.

A sequence-binding prepass resolves each image's index at that image's source generation. Legacy index blobs (v1/v2) and current v3 indexes are verified against their entry digests and bound image identities, then rebuilt from the migrated image framing. Metadata references are replaced, including forward references. One source index bound to different image identities is refused. The plan is capped by max_sequence_indexes (default 4096); indexed images may be read and rewritten repeatedly rather than retained. Unreferenced sequence blobs are opaque. Changed entries clear their cached head-size hint; ordinary metadata, summaries, keys and segment hash algorithms are preserved. Application-owned offsets and digests in opaque metadata are the caller's responsibility.

Opaque copying uses 64 KiB requests. Each image or nested archive has an encoded input/output cap (default 64 MiB), applied before reading the entry into memory. Nested archives are buffered under this same cap; arbitrary-size nested archives are not streamed recursively. Combined archive/image depth is limited (default 16). image_limits.plane_limits exposes the existing plane directory/record admission limits; their file/record byte limits cannot exceed the encoded cap. Storage includes source/output buffers, recursive rewrites, parser indexes, reader segment state and the bounded binding plan. These are admission limits, not a measured RSS ceiling. Exceeding a bound returns an error, never a successful partially upgraded result. The separate immutable-source/staging-sink and partial-output rules of upgrade_container also apply to upgrade.

IQA browser catalog profile

An archive can expose full-reference still-image pairs, thumbnails and stored scores through ordinary entries. Generic archives retain their existing key space. A browser selects this profile only if entry key 0 has the text attribute imij.profile = imij.iqa/v1. A key 0 used for another purpose continues to be an ordinary entry. The profile uses the archive's existing index, digest algorithm and append semantics.

The root blob is UTF-8 JSON, at most 65,536 bytes. The top-level object carries schema: "imij.iqa/v1", dataset: {id, name, metadata} and pairs: {firstPage, pageCount, pageSize, count}. Dataset metadata is a string map, such as citation, license and version. All keys and optional item ordinals use canonical decimal u64 strings. The first pair-page key is positive. Page keys are consecutive, with at most 1,000,000 pages of at most 128 pairs each. The final page has the remaining records.

Each page is an ordinary verified blob of at most 1 MiB, with {schema: "imij.iqa/v1/page", index, pairs}. The zero-based index agrees with the requested page. Each pair has a stable dataset-local id, reference, distorted, and scores. Optional strings source, distortion, level, and split describe dataset-native classifications.

  • An asset is {key, name, mediaType, digest}, with an optional thumbnail

    • entry key. The digest carries {id, bytes}, the archive digest algorithm ID and lowercase hexadecimal digest bytes in wire order. The key and digest bind the pair to the exact blob in the selected snapshot. This binding must be checked before returning scoring input. Thumbnails are presentation assets with separate keys.

  • A locator can declare an ordinal for an indexed sequence item. Use its

    • sequence-index binding and reconstruct the indicated item and its required references. Ordinary assets return the complete verified blob.

  • A score is {kind, name, value, source}. The kinds human and metric

    • keep the provenance visible. Finite optional min, max and std, boolean higherIsBetter and text version carry source information when supplied. Preserve the original numbers and direction. Unknown score fields can be ignored.

Keys resolve within the same immutable snapshot. A publisher updating an asset must also update the associated catalog binding and score provenance. URLs and the access method for archive ranges are publication metadata. An application can rebuild its browser view from the archive alone.
